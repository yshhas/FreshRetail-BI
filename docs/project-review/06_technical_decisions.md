# 第六章 关键技术决策与方案取舍

> 本章采用 ADR（Architecture Decision Record）结构：背景 → 问题 → 候选 → 对比 → 选择 → 理由 → 代价 → 影响。
> **A** = 文档/代码有直接依据；**B** = 由实现与上下文推断；**C** = 无法证实。
> 最后一节区分“已证实的历史决策”与“若重新设计可考虑的替代方案”。

## 6.2 D1：选择 FreshRetailNet-50K

### 背景

需要一个中国、真实、可公开、字段足够支撑经营分析的数据集。

### 问题

候选数据集要么非中国（Olist、UCI），要么无金额/订单/用户（淘宝、饿了么），要么许可不清（天猫、CUMCM），要么不可获取（MDPI、CnOpenData）。

### 候选对比

| 候选 | 优势 | 致命缺陷 |
|---|---|---|
| Olist | 9 表、可做完整闭环 | 非中国 |
| UCI Online Retail II | 真实交易、CC BY 4.0 | 单表、无类目、用户缺失 |
| 淘宝 UserBehavior | 规模大 | 无金额/订单/地区 |
| 饿了么 | 中国、规模大 | 曝光样本、金额是快照 |
| FreshRetailNet-50K | 中国、2024、门店×SKU×日、小时/缺货/折扣/天气 | 无金额、无用户、仅 90 天 |

### 选择

FreshRetailNet-50K（03 §I.1，A）。

### 理由

在“真实性、年份、字段完整度、许可清晰度”四维同时优于其他中国候选；能支撑销量、商品、区域、诊断四类分析。

### 代价

放弃金额、用户、订单、复购、留存、利润；只有 90 天；匿名 ID。

### 影响

- 项目更名为“销量经营分析”；
- 需求被裁剪；
- 所有文案禁止金额叙事。

### 如果重新设计

仍会选它，除非能获得真实企业的订单级数据；若目标是“完整电商闭环”，Olist 更合适，但会失去中国定位（B）。

## 6.3 D2：冻结结果 + 只读 BI，而不是动态重算

### 背景

P1–P4 产出大量分析结果，BI 需要展示与筛选。

### 问题

如果 BI 每次筛选都重算指标，会出现：

- 口径漂移（同一指标不同页面不同值）；
- 性能问题（4.5M 行反复扫描）；
- 无法证明“展示值 = 已验收值”。

### 候选

1. BI 直连明细，实时重算；
2. BI 读冻结 CSV/Parquet，只做筛选；
3. BI 建独立数据集市（ETL 复制 + 预聚合）。

### 对比

| 方案 | 一致性 | 性能 | 复杂度 | 可追溯 |
|---|---|---|---|---|
| 实时重算 | 低（易漂移） | 低 | 中 | 弱 |
| 读冻结结果 | 高 | 高 | 低 | 强 |
| 独立集市 | 中（需同步） | 高 | 高 | 中 |

### 选择

方案 2：读冻结结果 + manifest 校验（09 §0.2，A）。

### 理由

P1–P4 已经验收并冻结；BI 的职责是“展示与查询”，不是“第二套分析系统”。

### 代价

- 不能做“任意日期重算”；
- 新指标需要回到分析层；
- 冻结文件变更必须同步 manifest。

### 影响

- `freeze.verify_manifest()` 成为启动硬门槛；
- 所有 API 返回 `data_version`；
- 前端脚注反复强调“90 天冻结值”。

### 如果重新设计

仍会这样选。若业务需要实时指标，应另建“实时层”，而不是破坏冻结层（B）。

## 6.4 D3：DuckDB + Parquet，不建独立数据库

### 背景

4.5M 行明细、1.08 亿行小时展开；需要快速聚合；部署环境是单机 Windows。

### 问题

- pandas 全量加载内存压力大；
- PostgreSQL/MySQL 需要部署、建表、导数、权限、备份；
- 项目只读、无并发写。

### 候选

| 方案 | 部署成本 | 分析性能 | 事务/并发 | 适用性 |
|---|---|---|---|---|
| pandas | 低 | 中（小时展开吃力） | 无 | 小数据 |
| SQLite | 低 | 低（列式分析弱） | 有 | 事务型 |
| PostgreSQL | 高 | 高 | 强 | 服务型 |
| DuckDB | 低 | 高 | 单写多读 | 分析型 |
| Spark | 很高 | 高 | 强 | 大数据集群 |

### 选择

DuckDB 内存连接 + Parquet 视图（06 §4，A）。

### 理由

- 直接查 Parquet，数秒级；
- 无独立服务；
- 支持窗口函数、`unnest`、`generate_subscripts`；
- 结果仍是 Parquet，pandas/BI 可读。

### 代价

- 单机、单进程；
- 并发写不支持；
- SQL 方言与 PostgreSQL 有差异；
- CSV 视图无传统索引。

### 影响

- 数据管道与分析层都围绕 DuckDB 写 SQL；
- BI 层用同一引擎建只读视图；
- 性能优化靠 SQL（窗口函数）而非索引。

### 如果重新设计

仍会选 DuckDB。若数据增长 10–100 倍，考虑 Parquet 分区 + DuckDB 多进程，或 ClickHouse（B）。

## 6.5 D4：SQL 聚合 + pandas 后处理

### 背景

指标计算既可以用纯 SQL，也可以用纯 pandas。

### 问题

- 纯 pandas：小时展开 1.08 亿行，内存吃不消；
- 纯 SQL：分位、bootstrap、聚类、绘图不方便。

### 选择

“能在 SQL 里聚合的，先在 SQL 里聚合；需要统计/矩阵/绘图的，转 pandas”（06 §4、代码结构，A）。

### 理由

- SQL 负责“减少数据量”；
- pandas 负责“统计与呈现”；
- 两者分工清晰。

### 代价

- 同一指标可能有两套实现（`cleaning.py` 的 SQL/pandas 双版）；
- 需要测试保证一致。

### 影响

- `metrics.py` 全是 SQL；
- `analysis/*.py` 是 SQL + pandas 混合；
- `clean_frame` 用于单测，`select_clean_sql` 用于生产。

### 如果重新设计

仍会这样分工；但会把关键 SQL 抽成可测试的字符串模板，减少重复（B）。

## 6.6 D5：FastAPI + Pydantic v2

### 背景

需要把冻结数据变成只读 API，响应结构必须稳定。

### 候选

Flask、Django、FastAPI、Node/Express。

### 对比

| 方案 | 类型校验 | 文档 | 与数据层同语言 | 重量 |
|---|---|---|---|---|
| Flask | 手写 | 无 | 是 | 轻 |
| Django | 强（ORM） | 有 | 是 | 重 |
| FastAPI | 强（Pydantic） | 自动 | 是 | 中 |
| Express | 弱 | 手写 | 否 | 轻 |

### 选择

FastAPI + Pydantic v2（09 §4.3，A）。

### 理由

- Pydantic 模型就是响应契约；
- 自动 `/docs` 便于验收；
- 与 DuckDB/pandas 同语言；
- 异常映射简单（ValueError→400）。

### 代价

- 同步阻塞；
- 单 worker 并发有限；
- Pydantic v2 与部分旧生态不兼容。

### 影响

- `models.py` 定义所有响应；
- `main.py` 用 `Literal`/`Query` 做边界；
- 测试直接断言 JSON 结构。

### 如果重新设计

仍会选 FastAPI；多用户场景加 workers + 连接池（B）。

## 6.7 D6：URL 作为筛选状态真源

### 背景

多个页面有筛选、分页、组合选择，需要刷新恢复、可分享、可返回。

### 候选

1. 全局 store（Redux/Zustand）；
2. React Context；
3. URL search params；
4. localStorage。

### 对比

| 方案 | 刷新恢复 | 可分享 | 前进后退 | 复杂度 |
|---|---|---|---|---|
| 全局 store | 否 | 否 | 否 | 中 |
| Context | 否 | 否 | 否 | 低 |
| URL | 是 | 是 | 是 | 低 |
| localStorage | 是 | 否 | 否 | 低 |

### 选择

URL search params（09 §4.2、`useUrlFilters.ts`，A）。

### 理由

- 浏览器原生支持；
- 不需要额外状态库；
- 与返回/分享天然契合。

### 代价

- URL 可能很长；
- 需要处理非法参数；
- 复杂对象需要序列化。

### 影响

- `useUrlFilters.set/patch` 成为所有页面的状态入口；
- 任何非 page 参数变化都删除 page；
- E2E 直接断言 URL。

### 如果重新设计

仍会选 URL；但会把参数 schema 化（zod/valibot），减少手工解析（B）。

## 6.8 D7：前端不做聚合，后端统一抑制

### 背景

商品/门店详情需要展示组统计，n<20 时不能展示中位数。

### 问题

如果前端拿明细自己算，可能绕过抑制规则。

### 选择

- 后端输出组统计，n<20 时置空 + `suppressed=true`；
- 前端只显示 `—`；
- 明细接口明确“不做组统计”。

### 理由（09 §8.1 风险 2、`service.py`，A）

- 规则只在一处实现；
- 前端无法“算”出被抑制的值；
- 测试只需测后端。

### 代价

- 后端接口变多；
- 前端不能做灵活的临时聚合。

### 影响

- `store_groups`、`product_stores`、`pairs` 都有抑制逻辑；
- `Suppressed` 组件统一显示 `—`；
- E2E 检查 n<20 提示。

### 如果重新设计

仍会这样选。统计口径必须由后端拥有（B）。

## 6.9 D8：小样本策略（n<20 / SKU<10）

### 背景

门店规模差异大：10 家门店 SKU<10；某些四象限×结构群组合只有 7–17 家。

### 问题

小样本的中位数/比例不稳定，展示出来会误导。

### 候选

1. 全部展示，加警告；
2. 小于阈值不展示；
3. 合并单元格。

### 选择

- 组统计 n<20：不展示中位数/比例，显示 `—`；
- SKU<10 门店：不进入风险诊断、不参与四象限/同类比较；
- 共现 <20 店：不展示，但报告数量。

### 理由（P3-B/P3-C/P4、`service.py`，A）

- 统计稳定性；
- 避免“7 家门店的中位数”被当成结论；
- 保持“可解释的缺失”。

### 代价

- 部分页面看起来“空”；
- 用户可能误以为“没有数据”。

### 影响

- `Suppressed` 组件 + 文案解释；
- 10 家门店在 `v_store` 中 `diagnosis_status='不适用'`；
- 共现页五态文案。

### 如果重新设计

仍会保留抑制，但会把阈值做成可配置，并在页面显示“为什么是 —”（B）。

## 6.10 D9：精确组合与至少组合双口径

### 背景

风险分析需要回答两类问题：

- “只命中这两个域的门店有多少？”（精确）
- “至少命中这两个域的门店有多少？”（至少）

### 问题

两个问题都合理，但答案不同（38 vs 56），混用会误导。

### 候选

1. 只保留精确；
2. 只保留至少；
3. 双口径并列。

### 选择

双口径并列，UI 可切换（P4-B、P3-D、C-2/C-3，A）。

### 理由

- 精确适合“看组合结构”；
- 至少适合“看风险覆盖”；
- 两者回答不同问题，不能互相替代。

### 代价

- 页面复杂；
- 用户需要理解差异；
- API 需要两套参数（`exact_combo` / `domains`）。

### 影响

- 风险页有“恰好命中/至少同时命中”切换；
- `v_risk_exact`（16）与 `v_risk_at_least`（10）；
- 测试分别锁定 38/56。

### 如果重新设计

仍会双口径；但会把“38 ⊂ 56”的关系直接画在页面上，减少解释成本（B）。

## 6.11 D10：`returnTo` + 浏览器历史双机制

### 背景

跨页下钻需要“返回上一页并保留筛选”。

### 候选

1. 只用 `returnTo`；
2. 只用浏览器历史；
3. 两者结合。

### 对比

| 方案 | 多级返回 | 刷新恢复 | 可分享 | 复杂度 |
|---|---|---|---|---|
| 只用 returnTo | 会丢上层 context | 是 | 是 | 低 |
| 只用历史 | 是 | 否 | 否 | 低 |
| 结合 | 是 | 是 | 是 | 中 |

### 选择

结合（C-1/C-4，A）：

- 有站内历史：`nav(-1)`；
- 刷新/直达：`returnTo`；
- 非法：默认页。

### 理由

浏览器历史天然保存完整链路；`returnTo` 解决“刷新后没有历史”的问题。

### 代价

- 需要判断 `location.key !== 'default'`；
- 安全校验复杂（S-01）。

### 影响

- `BackLink` 组件；
- `safeReturnTo` 8 道校验；
- C-4 多级返回 E2E。

### 如果重新设计

仍会结合；但会把导航状态做成显式栈（便于测试），而不是依赖浏览器历史（B）。

## 6.12 D11：真实冻结数据测试 + 数字断言

### 背景

数据项目的测试很容易变成“跑通即可”，无法防止口径漂移。

### 选择

- pytest 直接读真实冻结 CSV/Parquet；
- 断言关键数字（888/117/35/38/56/16/10）；
- E2E 断言页面文案与数量；
- 单测用合成小样本测边界。

### 理由（`tests/`、`bi/tests/`、E2E，A）

- 数据项目的“正确性”就是数字一致；
- 冻结数字是最强的回归保护；
- 合成样本适合测边界（MAD=0、空值、异常折扣）。

### 代价

- 测试与数据强耦合；
- 数据重冻结会导致大面积失败；
- 测试运行需要真实数据文件。

### 影响

- CI（若有）必须挂载数据；
- 测试数量随阶段增长（18→101）；
- 数字变更必须同步测试与文案。

### 如果重新设计

仍会保留“冻结数字断言”，但会增加“从 manifest 生成期望值”的机制，减少手工同步（B）。

## 6.13 D12：不引入 Docker/Redis/MQ/AI/预测

### 背景

项目有“作品集展示”诉求，容易过度工程化。

### 选择

明确不做（09 §8.3，A）：

- 不做实时接入、消息队列、复杂权限/多租户；
- 不做 AI Agent、RAG、自动诊断/决策；
- 不做用户留存、利润、库存、客流、订单分析；
- 不重算 P1–P4。

### 理由

- 数据不支持；
- 单机只读不需要；
- 增加依赖会提高演示门槛。

### 代价

- 无容器化交付；
- 无公网部署；
- 无实时能力。

### 影响

- 运行需要 Python + Node 环境；
- Docker 成为“下一步”而非“已完成”；
- 项目边界清晰。

### 如果重新设计

仍会拒绝 AI/实时；但会把 Docker Compose 作为“演示交付”的优先项（B）。

## 6.14 D13：自研 `useApi`，不引入 React Query/Zustand

### 背景

09 设计方案建议 React Query 缓存 + Zustand 存 UI 状态；实际代码只用了自研 `useApi` + URL。

### 问题

是否值得为只读、低频请求引入两个状态库？

### 候选

1. React Query + Zustand（设计建议）；
2. SWR；
3. 自研 `useApi` + URL。

### 选择

方案 3（`useApi.ts`，A）。

### 理由（B）

- 请求简单：GET、无 mutation、无重试；
- URL 已承担筛选状态；
- 减少依赖与学习成本。

### 代价

- 无缓存/去重/后台刷新；
- 页面切换重复请求；
- 复杂场景需要手写 loading/error。

### 影响

- 每个页面自己管理 `useApi`；
- 切换筛选会重新请求；
- 性能主要靠后端。

### 如果重新设计

页面数量增加后，会引入 React Query；当前规模下自研是可接受的（B）。

## 6.15 D14：CSV 导出只给聚合表 + 注释头

### 背景

用户可能需要把门店列表导出。

### 选择

`/api/v1/export/stores.csv`：

- 只导出聚合门店表（23 列）；
- 前 4 行注释：`# data_version`、`# period`、`# filters`、`# note`；
- 不导出原始 SKU-日明细。

### 理由（`service.export_stores_csv`，A）

- 避免泄露明细；
- 保持可追溯（版本/期间/筛选）；
- 与“只读聚合”定位一致。

### 代价

- 不支持组合筛选参数；
- 无公式注入转义；
- 导出能力弱于页面筛选。

### 如果重新设计

会把导出参数与页面完全对齐，并对单元格做 `=`/`+` 前缀转义（B）。

## 6.16 D15：依赖漏洞暂不升级（技术债）

### 背景

BI-1 阶段 `npm audit` 报 9 项漏洞（2 critical / 1 high / 6 moderate），涉及 `echarts`、`react-router-dom` 等。

### 候选

1. 立即 `npm audit fix`；
2. 手动升级主依赖；
3. 记录并延后。

### 代价

### 影响

- 技术债文档保留升级路径；
- 本轮未新增依赖。

### 如果重新设计

仍会延后，但会把“升级 + 全量回归”写成明确的门禁（B）。
