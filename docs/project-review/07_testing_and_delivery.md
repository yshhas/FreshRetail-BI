## 7.1 测试体系全景

项目没有采用传统“单元 70% / 集成 20% / E2E 10%”的金字塔，而是按“数据项目”的特点组织：

```
① 契约测试（数据文件、字段、切分）        pytest
② 清洗与指标测试（规则、边界、公式）      pytest
③ 分析回归测试（锁定冻结数字）            pytest
④ API 契约/安全/并发测试                  pytest + TestClient
⑤ 纯函数测试（格式化、导航安全、商品逻辑）vitest
⑥ 真实浏览器 E2E（页面行为、下钻、返回）  Playwright
⑦ 构建与冻结校验（tsc、vite、SHA-256）    命令行
```

**E2E 的特点（A/B）**：

- 直接驱动本机 Chrome（`playwright-core` + `executablePath`）；
- 使用真实 API + 真实冻结数据，不 mock；
- 断言具体数字与文案，而不是“页面存在”；
- 缺点：依赖本机 Chrome 路径、运行慢、无 CI。

## 7.4 测试数据与 Mock 策略

| 测试类型 | 数据来源 | 是否 Mock |
|---|---|---|
| 契约测试 | 真实 `train.parquet` 元数据 | 否 |
| 清洗测试 | 合成小 DataFrame | 否（纯函数） |
| 指标测试 | 内存 DuckDB + 小样本 | 否 |
| 分析回归 | 真实冻结 CSV | 否 |
| API 测试 | FastAPI TestClient + 真实数据 | 否 |
| 前端单测 | 纯函数输入 | 否 |
| E2E | 真实 API + 真实浏览器 | 否 |

**结论**：项目几乎不使用 Mock，代价是测试依赖真实数据文件与环境；好处是测试结果接近真实运行（A）。

## 7.5 自动化与 CI

### 现状

- 无 `.github/workflows`、无 Jenkins/GitLab CI 配置（A：目录检查）。
- 测试靠本地命令：

```powershell
python -m pytest -q
npm test -- --run
node tests/e2e.mjs
node tests/e2e-products.mjs
node tests/e2e-c1.mjs
node tests/e2e-c2.mjs
node tests/e2e-c3.mjs
node tests/e2e-c4.mjs
npm run build
```

### 影响

- 没有“每次提交自动跑”的保护；
- 没有测试报告归档；
- 无法阻止“忘记跑测试”的回归。

### 建议（B）

- 加 GitHub Actions：pytest + vitest + build；
- E2E 用 `@playwright/test` + 容器化 Chrome；
- 把冻结校验作为 CI 的独立 job。

## 7.11 生产可靠性评估

### 可以支持的场景

- 本机单用户演示；
- 内部评审、作品集展示；
- 只读查询、筛选、下钻；
- 数据口径追溯与复算。

### 不能支持的场景

- 公网多用户访问；
- 写入、审批、权限管理；
- 实时数据接入；
- 大数据量扩展（>10 倍）；
- 高可用/容灾。

### 结论（B）

这是一个**高质量的本地分析型 BI 演示系统**，不是生产级 SaaS。它的强项在“口径、可追溯、测试锁定”，弱项在“部署、并发、安全、运维”。
