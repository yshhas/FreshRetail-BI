# 第一章 项目起源与背景

> 证据等级：本章事实主要来自 01–06、09 报告与 `src/freshretail/config.py`，标注为 **A（直接证据）**；对“为什么这样想”的解释若无原文依据，标注 **B（推断）**。无证据处标 **C**。

---

## 1.1 项目名称与定位

项目全称：**中国数字零售与本地生活经营增长分析**。

最终交付形态：一套 **FreshRetailNet-50K 零售经营 BI**——只读、可追溯、可在本地浏览器演示的经营分析网站。

产品定位（《09_BI产品需求与技术架构设计方案》§1.1，A）：

> 用已验收的 P1–P4 指标，回答“哪里、哪类门店、哪类商品、哪类风险值得复核”，不提供经营评分、门店排名或因果结论。

它明确“不是”：

- 不是实时交易/库存/补货系统；
- 不是 AI Agent/RAG/自动决策系统；
- 不是销售额/GMV/利润分析平台；
- 不是门店绩效考核或奖惩排名工具。

---

## 1.2 最初想解决什么问题

第一阶段的设想并不是“做一个 BI 网站”，而是一条完整的**六模块经营诊断闭环**（01 报告 §6，A）：

```
企业整体经营 → 用户价值 → 留存/复购 → 商品经营 → 区域市场 → 诊断策略
```

这个闭环要成立，前提是拥有一份**订单级交易明细**：订单 ID、金额、时间、用户、商品同时具备（01 §6，A）。

现实业务场景被设定为：中国即时零售/生鲜前置仓的门店经营分析，同时兼顾“可公开作品集展示”的诉求（01 §1、03 §D.3、04 §2，A）。

目标用户在前期文档中**没有正式定义**；直到 09 设计方案 §1.2 才形式化为 6 类角色（A）：

| 角色 | 主要诉求 |
|---|---|
| 经营负责人 | 总览、城市/风险分布 |
| 城市/区域运营 | 城市对比、城市内门店画像 |
| 门店运营 | 单店档案、同类对比、复核清单 |
| 商品/品类运营 | SKU 贡献、类别结构、风险商品 |
| 数据分析师 | 联动筛选、下钻、口径查询 |
| 数据管理员 | 数据版本、冻结清单、接口状态 |

> **复盘判断（B）**：用户角色是在数据选型之后才补齐的，带有明显的“数据倒推需求”痕迹。这不是缺陷，但说明项目本质上是“以数据可行性为第一约束”的作品集型项目，而不是“先有客户、再找数据”的商业项目。

## 1.3 用户原本如何解决这些问题，原方式有什么缺陷

文档没有真实的“客户现状访谈”。可从候选数据与业务逻辑推断（B）：

- 零售/即时零售团队通常用 Excel + SQL + 人工报表回答“哪些门店、哪些 SKU 有问题”；
- 这种方式的问题是：口径不统一、重复取数、指标不可追溯、下钻靠人工、图表与结论脱节。

项目要解决的正是这些工程问题：

1. 把指标口径固化成可复现的代码；
2. 把“分析结果”与“展示层”分离，避免每次看数都重算；
3. 让筛选、下钻、返回状态可恢复；
4. 让每个数字都能追溯到字段、公式与样本。

这些目标在 06 §1、09 §0.2、§8.2 中有直接表述（A）。

## 1.4 为什么需要开发这个系统

如果只是“做一份数据分析报告”，静态图表就够了。项目最终选择做 BI，原因在 09 §0.2 与 §9 中写得很清楚（A）：

- P1–P4 已经产出了大量冻结结果（CSV/Parquet），但只能通过报告阅读；
- 报告无法支持“按城市/门店/风险组合/商品筛选后再看”；
- 需要把分析结果变成可交互、可分享、可刷新恢复的查询层；
- 但不能重新计算指标，否则会破坏已验收口径。

因此，BI 的定位是“在冻结分析结果之上的只读展示与查询层，不是第二套分析系统”（09 §0.2，A）。

核心价值可以概括为四点：

1. **口径可信**：所有数字来自冻结结果，前端不做聚合；
2. **可追溯**：manifest + SHA-256 + `data_version`；
3. **可下钻**：城市→门店→SKU→商品，筛选状态写 URL；
4. **可演示**：本地一条命令启动，浏览器直接展示。

## 1.5 数据选型的两次推翻

这是项目最真实、也最能体现“研发历程”的部分。证据来自 01–03 报告（A）。

### 1.5.1 第一轮：六模块 → 找不到任何一套数据能支撑

01 §8 的结论非常直接：

> 若坚持六大模块不得缩减，方案 A 不足以支撑项目；没有任何一套数据能完整支持六大模块中的任何一个模块。

第一轮核验了大量候选数据集，典型问题如下（01/02，A）：

| 候选 | 规模/时间 | 主要缺陷 |
|---|---|---|
| Olist（巴西） | 约 10 万订单、9 表、2016–2018 | 非中国；无退款、成本、品牌 |
| UCI Online Retail II | 1,067,371 行、2009–2011 | 单表、无类目、约 1/4 CustomerID 缺失 |
| 淘宝 UserBehavior | 1 亿条、9 天 | 无金额、无订单、无地区 |
| 天猫订单报表 | 28,010 行 | 无 user_id、无商品；链接失效、许可不明 |
| 天池母婴 | 8.40 MB 样本 | 无金额；许可条款冲突 |
| 美团 TSL | 654,343 运单 | 无金额、无商品、无消费者 ID |
| CnOpenData | 3 表、行数未公开 | 付费、缺用户/订单/时间 |
| 饿了么 | 1.28 亿样本、8 天 | 曝光样本非订单；金额为快照 |
| TAOBAO-MM | 8.79M 用户、99M 样本、139 GB | 仅点击标签，无金额 |
| CUMCM 2023 C | 4 附件、2020–2023 | 单店无地区；许可不明 |

### 1.5.2 第二轮：首选 Olist，但与中国定位冲突

02 §G.1 首选巴西 Olist，理由是它是“唯一可支撑完整经营诊断闭环”的候选；但 §H.1 同时承认：若坚持中国市场定位，没有合适的核心数据源（A）。

这形成第一次真正的方案分叉：

- 方案 A：放弃中国定位，用 Olist 做完整闭环；
- 方案 B：坚持中国定位，缩减模块；
- 方案 C：继续寻找中国数据源。

### 1.5.3 第三轮：FreshRetailNet-50K 胜出

03 报告找到 FreshRetailNet-50K（Dingdong-Inc，CC BY 4.0），并在“真实性、年份、字段完整度、许可清晰度”四个维度同时优于此前全部中国候选（03 §C.1、§F、§I.1，A）。

最终选择它的原因（A）：

- 中国、2024 年、真实零售场景（生鲜前置仓）；
- 4.85M 行、50,000 条门店×SKU 序列、898 门店/18 城市/865 SKU；
- 字段包含销量、小时销量、缺货状态、折扣、天气、节假日/活动标记；
- CC BY 4.0，允许公开作品集展示；
- 数据结构稳定，可做完整的数据契约与冻结。

代价（03 §I.1，A）：

- **没有金额**：`sale_amount` 是全局归一化销量，不是销售额；
- **没有订单/用户**：无法做客单价、复购、留存、RFM；
- **只有 90 天**：无法做年度/季节长期趋势；
- 城市/门店/商品均为匿名 ID，无真实名称。

这是一次典型的**用“分析范围”换“数据真实性”**的取舍。

## 1.6 数据获取与质量核验

04 报告记录了完整核验过程（A）：

| 项 | train | eval |
|---|---|---|
| 文件大小 | 106,436,287 B | 8,440,124 B |
| SHA-256 | `6706832d…de5a3d` | `1b118840…995e960e` |
| 行数 | 4,500,000 | 350,000 |
| 列数 | 19 | 19 |
| 日期范围 | 2024-03-28 ~ 2024-06-25（90 天） | 2024-06-26 ~ 2024-07-02（7 天） |
| 主键 | `(dt, store_id, product_id)` 零重复 | 同左 |
| 空值/重复行/负值 | 0 / 0 / 0 | 0 / 0 / 0 |
| 门店 / 城市 / SKU | 898 / 18 / 865 | — |
| 类目层级 | 32 / 84 / 233 | — |

关键异常与处理（04 §3–§7，A）：

- `discount=0` 共 16,039 行（0.36%），与官方“1.0=无折扣”冲突，视为缺失；
- `discount>1` 共 34 行，促销分析时排除；
- `sale_amount=0` 共 200,760 行（4.46%），其中 76.62% 伴随缺货；
- `hours_sale` 合计与 `sale_amount` 最大误差 1.4e-14，证明小时字段自洽；
- **最重要的口径纠正**：`sale_amount` 是“全局归一化后的销售数量”，不是金额、不是件数。第三阶段“可能为万元”的推测作废（04 §7、附录 B）。

> **复盘判断（B）**：这次口径纠正如果晚发生，后面所有报告、图表、BI 都会建立在“销售额”的错误叙事上。它是整个项目最有价值的一次“停下来纠正”。

train/eval 按时间切分，无重叠、eval 紧接 train。项目从分析阶段开始约定**不读取 eval**（05 §8.4、09 §8.2，A）；04 阶段的读取属于“数据质量核验”，与“分析/BI 使用”不同，但文档没有显式区分这两种读取。

## 1.7 从模糊想法到明确需求

05 报告是需求真正收敛的地方。它做了三件事（A）：

### 1.7.1 保留并重定义

| 原模块 | 调整后 | 说明 |
|---|---|---|
| 模块一 企业整体经营 | 销量经营状况 | 只保留量口径 |
| 模块四 商品经营 | 商品销量与缺货经营 | 保留 |
| 模块五 区域市场 | 区域销量对比 | 保留 |
| 模块六 诊断策略 | 运营诊断与策略 | 保留，但禁止因果结论 |

### 1.7.2 删除

GMV、销售额、客单价、订单量、退款率、支付/利润分析、用户数、新老客、RFM、复购率、留存率、Cohort、流失预测、区域客单价、配送时效等（05 §2.2，A）。

### 1.7.3 降级为“数据能力边界”说明

模块二（用户价值）、模块三（留存复购）不再产出指标，只说明“为什么不能做”（05 §2.2、06 §1，A）。

> **复盘判断（B）**：这是一次“删需求”而不是“加功能”的产品决策，难度高于写代码。它奠定了后续所有阶段的边界：没有用户就不做用户分析，没有金额就不做金额分析。

## 1.8 核心业务流程与用户使用流程

### 1.8.1 数据侧业务流程

```
原始 Parquet（只读）
  → 文件级校验（大小 + SHA-256）
  → 元数据契约（行/列/字段/类型）
  → 原始质量检查（空值/主键/负值/日期）
  → 清洗（仅新增派生列，不删行、不填补）
  → 派生聚合（日/小时/门店/商品/城市/诊断）
  → P1–P4 分析（CSV + PNG + 报告）
  → 冻结（manifest 25 项 SHA）
  → BI 只读视图（DuckDB）
  → FastAPI
  → React/ECharts
```

这条链路在 06 §3、09 §4.1 中有直接对应（A）。

### 1.8.2 用户侧使用流程

1. 打开经营总览，确认样本规模（898/888）与数据版本；
2. 进入城市与门店，按城市/象限/结构群/风险域筛选；
3. 点击门店进入详情，查看风险标记、同类比较、SKU 列表；
4. 从门店 SKU 进入商品详情，再返回；
5. 进入经营风险，选择精确组合或至少组合，查看门店；
6. 进入商品 BI，按风险/类别/覆盖筛选，查看 SKU 详情与同店共同出现；
7. 所有筛选写入 URL，可刷新、可分享、可逐级返回。

该流程与实际路由、E2E 场景一致（`App.tsx`、C-1/C-2/C-3/C-4 E2E，A）。

## 1.10 需求优先级

从实际开发顺序可以清晰看出优先级（A/B）：

1. **数据可信**（校验、清洗、契约）——没有它后面都不成立；
2. **分析口径**（P1–P4）——先有结论，再有展示；
3. **冻结**（manifest）——保证展示不会“漂移”；
4. **只读 API**（BI-0）——先打通数据到接口；
5. **第一批页面**（BI-1：总览、城市、风险、门店）；
6. **商品 BI**（BI-2-A/B）——数据资产增量 + 五个页面；
7. **跨页联动**（BI-2-C）——最后做复杂下钻与状态管理；
8. **容器/公网**——明确未做。

> **复盘判断（B）**：这个顺序是合理的“先难后易、先地基后装修”。如果先做页面，后面口径一变，全部返工。

## 1.12 项目如何定义“完成”

项目没有单一的“上线”标准，而是分阶段定义完成（06 §10、09 §8.2，A）：

- **数据阶段**：哈希一致、清洗前后行数一致、派生表非空、测试全通过；
- **分析阶段**：每个阶段有报告、图表、验收记录，关键数字可复算；
- **BI 阶段**：每个阶段有实施报告、独立审计、整改、复核、验收/冻结；
- **整体**：pytest + vitest + E2E + build + 25 项 SHA 全部通过。

这是一种“**验收驱动**”的完成定义，而不是“功能上线”定义。
