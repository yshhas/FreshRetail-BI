## W017 P1 三层口径与日趋势

### 工作背景

W016 之后，派生表已经就绪。第一个分析问题是：**整体销量是什么走势？**

### 输入

`agg_daily`、`agg_hour_profile`、`agg_hour_weekday`、`agg_store_day`、`agg_store_summary`、`agg_product_summary`、`clean_train`。

### 实际步骤

1. `load_inputs()` 读取 7 张派生表；
2. `build_daily()` 按日期排序，计算 7 日均线、日环比、稳健 z、星期；
3. 产出 `t1_daily.csv`；
4. 生成 f1 趋势图。

### 核心原理

“日均”必须说明分母。P1 保留三层：

| 口径 | 公式 | 用途 |
|---|---|---|
| 样本总指数 | `SUM(sales_index)` | 看整体形状 |
| 单店日均 | `SUM / 门店-日数` | 横向比较门店/城市 |
| 单序列日均 | `SUM / 序列-日数` | 比较商品，需同时看覆盖 |

### 产物

`t1_daily`、`t2_weekday`、`t3_hour`、`t4_heatmap`、`summary.json`、f1–f9。

### 运行实例（真实数据）

`agg_daily` 第一行：

| dt | sales_index_total | per_store_index |
|---|---:|---:|
| 2024-03-28 | 35,787.337 | 39.852268 |

90 天总指数 4,493,660.787；日总指数范围 34,893–72,939。

### 遇到的问题

总指数会随门店数变化，不能直接当“企业销售额”；单序列日均会受覆盖影响。因此三层都保留。

### 验证

`tests/test_metrics.py::test_daily_summary`；P1 报告数字与冻结值一致。

### 下游

W018 异常日、W020 门店分布。

## W018 异常日：稳健 z（MAD）

### 工作背景

需要识别“哪几天销量异常”。均值 ± 3σ 在长尾数据上不可靠。

### 输入

`agg_daily.sales_index_total`。

### 实际步骤

1. 计算中位数 `med`；
2. 计算 MAD = `median(|x - med|)`；
3. `robust_z = (x - med) / (1.4826 × MAD)`；
4. `|robust_z| > 3` 判为异常；
5. 输出 `t5_anomaly_days.csv` 与 f7 图。

### 核心原理

MAD 不受极端值影响；1.4826 是正态分布下 MAD 与标准差的换算系数。这样得到的 z 与标准 z 尺度接近，但更稳健。

### 产物

`t5_anomaly_days.csv`、`diag_anomaly_days.parquet`。

### 运行实例

90 天中只有 1 天被判定为异常（稳健 z = 3.26）。

### 遇到的问题

如果 MAD=0（大量相同值），z 无法计算；P1 的日级数据没有触发，但 P2 的序列级触发了 75 条，后来单独披露。

### 验证

`tests/test_metrics.py::test_anomaly_days_and_health_score`。

### 下游

P3-D 的 R6（高异常日）使用 `anomaly_rate`。

## W019 持续低销：7 日滚动 + 门店中位

### 工作背景

“某天卖得少”不是问题，“连续多天低于自己的正常水平”才是。

### 输入

`agg_store_day`（门店×日指数）。

### 实际步骤

1. 对每家门店按日期排序；
2. 计算 7 日滚动均值；
3. 以门店自身中位数为基准，低于 `0.7 × median` 记为低销；
4. 统计最长连续天数；
5. 只把 `>=7 天` 的门店写入 `t11`。

### 核心原理

用门店自己的中位数做基准，避免“小店永远低销”的误判；用连续天数过滤单日波动。

### 产物

`t11_sustained_low.csv`、`max_low_run_days` 字段。

### 运行实例（关键代码）

```python
roll = s.rolling(7, min_periods=7).mean()
flag = (roll < 0.7 * base).fillna(False).to_numpy()
```

### 遇到的问题

只输出 ≥7 天的门店，导致 P3-B 合并时对未达标门店 `fillna(0)`；真实 1–6 天的 54 家门店信息丢失。这个问题在 P3-D 才被修复。

### 验证

P3-D 用 `low_run_table` 独立复算，恢复 54 家，R3 命中仍为 90。

P3-D 的 R3（W032）。

## W021 P2 SKU 规模/效率双榜

### 工作背景

商品分析不能只看“卖得多”，还要看“单店效率”。两者经常矛盾。

### 输入

`clean_train`、`agg_product_summary`。

### 实际步骤

1. `load_base` 用 DuckDB 计算每个 SKU 的总指数、覆盖门店数、序列天数、单序列日均、动销率、缺货率、促销率；
2. 计算 SKU 跨门店 HHI；
3. `add_sku_metrics` 计算份额、累计份额、规模/效率排名差；
4. 输出 `t1_sku_metrics`。

### 核心原理

总量 = 覆盖 × 单店效率。只看总量会奖励“铺货广”，只看效率会忽略“覆盖窄”。双榜能暴露这种矛盾。

### 产物

`t1_sku_metrics.csv`（865 行、40 列）。

### 运行实例（真实数据）

| SKU | 覆盖门店 | 单序列日均 | 总指数 | 规模排名 | 效率排名 |
|---|---:|---:|---:|---:|---:|
| P0268 | 131 | 15.555 | 183,395.1 | 1 | 1 |
| P0005 | 783 | 2.601 | 183,265.3 | 2 | 20 |

P0268 覆盖窄但效率高；P0005 覆盖广但单店效率低。排名差为 -18。

### 遇到的问题

效率榜受覆盖影响；因此设置“覆盖 ≥5 店”门槛（540 个 SKU）。

### 验证

`tests/test_p2.py::test_share_and_rank`、`test_p2_audited_numbers_unchanged`。

### 下游

W022 Pareto/覆盖敏感性、W023 风险旗标。

## W023 P2 四个风险旗标

### 工作背景

需要从 865 个 SKU 中筛出“值得复核”的 SKU：高波动、高零销、异常日频繁、门店集中。

### 输入

`t1_sku_metrics`。

### 实际步骤

1. 计算 P95 阈值：CV 1.060、零销 24.44%、HHI 0.184；
2. 高波动：`cv_series_median > P95`；
3. 高零销：`zero_rate > P95`；
4. 异常日频繁：`anomaly_rate > 5%`；
5. 门店集中：`store_count >= 5` 且 `hhi > P95`（避免单店 HHI=1 误判）；
6. 汇总 `risk_flag_count`。

### 核心原理

四个旗标相互独立，不是 AND。命中数量只表示“命中了几条筛查规则”，不是风险评分。

### 产物

`t9_sku_risk_flags.csv`（117 行）、`flag_*` 字段。

### 运行实例（关键代码）

```python
q_hhi = d.loc[d["store_count"] >= 5, "hhi"].quantile(0.95)
d["flag_store_concentration"] = (d["store_count"] >= 5) & (d["hhi"] > q_hhi)
d["risk_flag_count"] = d[[...]].sum(axis=1)
```

结果：748 个 0 旗标、82 个 1 旗标、23 个 2 旗标、12 个 3 旗标；总计 117。

### 遇到的问题

读者容易把“异常 SKU”理解成“四个条件同时满足”；报告后来补充说明四个旗标相互独立。

### 验证

`test_p2.py::test_anomaly_flags_ignore_single_store_hhi`、`test_p2_audited_numbers_unchanged`。

### 下游

BI 商品总览/风险页（W055）、P4-C 风险 SKU 分布（W036）。
