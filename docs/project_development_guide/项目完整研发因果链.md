# 项目完整研发因果链

> 这份文档只做一件事：把 66 个工作单元串成一条“为什么发生、产生什么、又引出什么”的链。
> 详细实现见各分册；这里关注因果关系。

---

## 第一段：想法 → 找数据（W001–W004）

**起点**：项目想覆盖企业经营、用户、留存复购、商品、区域、诊断六个模块。

**隐含前提**：需要订单级数据（订单 ID、金额、时间、用户、商品）。

**第一次现实检查**：第一轮候选数据集核验（W002）发现，没有任何公开数据能同时满足五要素 + 中国 + 可公开。

**分叉**：Olist 能闭环但不是中国（W003）。项目没有立刻放弃中国定位，而是继续找（W004）。

**结果**：找到 FreshRetailNet-50K。它有中国、真实、2024、CC BY 4.0，但没有金额、没有用户、只有 90 天。

**因果**：没有金额 → 后面不能做金额分析；没有用户 → 不能做复购/留存；只有 90 天 → 不能做长期趋势。这个选择直接决定了 W008 的需求裁剪。

---

## 第二段：选型 → 口径危机（W005–W007）

**为什么先校验**：镜像站可能不一致，文件可能截断；如果文件不对，后面全错。

**结果**：两个文件大小与 SHA-256 都与官方一致（W005）。

**质量检查**（W006）：4.5M 行、零重复/空值/负值；但 `discount=0` 16,039 行、`discount>1` 34 行、零销 200,760 行、长尾偏度 8.47。

**关键发现**（W007）：`sale_amount` 不是金额，是全局归一化销量。

**因果**：这个发现推翻了第三阶段的金额叙事，迫使项目从“金额经营分析”转为“销量经营分析”。如果没发现，后面所有报告、BI 都会建立在错误单位上。

---

## 第三段：需求裁剪 → 数据基础设施（W008–W016）

**需求裁剪**（W008）：保留销量、商品、区域、诊断；删除金额、用户、复购、留存、订单、利润；模块二/三降级为“数据能力边界”。

**因果**：范围确定后，才能决定数据怎么存、怎么算。

**基础设施**（W009–W016）：

- W009 分层：raw 只读、derived 可重建、logs 可追溯；
- W010 契约：文件/字段/主键/日期/切分；
- W011 清洗：只加列、不删行；
- W012 SQL/pandas 双实现；
- W013 DuckDB + Parquet；
- W014 13 张派生表；
- W015 流水线 + JSONL；
- W016 18 项测试。

**因果**：派生表让 P1 不必每次扫描 4.5M 行；契约让“数据坏了”在启动时就失败；日志让没有 Git 的项目仍能追溯运行。

---

## 第四段：P1 → P2 → 第一次审计（W017–W024）

**P1**（W017–W020）先回答整体趋势、异常日、门店差异、持续低销。

- W017 三层口径：总指数、单店日均、单序列日均；
- W018 稳健 z：中位数/MAD，避免长尾拉偏；
- W019 持续低销：7 日滚动 + 门店中位 70%；
- W020 门店分布/四分位。

**P2**（W021–W023）转向商品：

- W021 规模/效率双榜：P0268 覆盖 131 店、效率 15.56；P0005 覆盖 783 店、效率 2.60；
- W022 Pareto：Top10% 贡献 72.30%；覆盖门槛变化会让 Top10 大幅换人；
- W023 四旗标：117 个风险 SKU、35 个多风险。

**审计**（W024）：发现“单店日均”分母是 SKU-门店-日，不是门店-日；C05 1.184 vs 14.545。修正为两个指标。

**因果**：这次审计让项目意识到“名字/分母/边界”比公式更容易错，也奠定了后面“每阶段独立审计”的做法。

---

## 第五段：P3 四块 → 口径系统（W025–W033）

**P3-A**（W025–W026）：城市对比，先解决两个缺货口径；小城市不排名；bootstrap 1,000 次。

**P3-B**（W027–W028）：门店分层，用 Huber RLM 控制规模；四象限 261/183/183/261；审计发现 R² 命名问题。

**P3-C**（W029–W031）：商品结构，HHI/熵/等样本十分位/Ward 聚类；审计发现 bootstrap 行序问题。

**P3-D**（W032–W033）：风险标记 R1–R8；五域；精确/至少组合；审计发现整体缺货率二次加权、54 家低销门店被 `fillna(0)`、bootstrap 样本量硬编码。

**因果**：P3 结束时，项目不再只有“指标”，而是有了一套口径体系：三层销量、两种缺货、三种率、精确/至少、运营域/结构提示。P4 和 BI 全部建立在这套口径上。

---

## 第六段：P4 整合 → 冻结（W034–W040）

**P4-A**（W034）：把 P1–P3 合成一行一店（898×42）。

**P4-B**（W035）：诊断规则 + 16 种精确组合 + 至少组合 + 规则库。精确“缺货+高零销”38，至少 56。

**P4-C**（W036–W037）：50,000 行门店×SKU incidence、1,237 对共现、16 格四象限×结构群。

**审计整改**（W038）：n<20 单元格显示 `—`；“同时销售”改为“观察期内同店共同出现”；规则库补层次。

**冻结**（W039）：22 个结果文件 → SHA-256 manifest；后来扩到 25。

**因果**：冻结把“分析结果”变成“不可变事实”，BI 才敢只读展示。没有冻结，页面数字随时可能被重跑覆盖。

---

## 第七段：BI 后端 → 只读 API（W041–W047）

**设计**（W041）：只读 BI、6 类角色、9 页、FastAPI + DuckDB + React。

**视图**（W042）：25 个只读视图；`v_store` 三表合并；`v_risk_at_least` 去对角线。

**冻结校验**（W043）：启动即校验 25 项，失败拒绝启动。

**契约**（W044）：`data + meta + warnings`；分页 ≤200；白名单。

**门店/风险/商品 API**（W045–W047）：筛选、抑制、导出、组合、商品、性能优化、只读安全。

**因果**：API 让前端不必知道文件路径与 SQL；`meta` 让每个响应自带样本量、版本、抑制状态。

---

## 第八段：BI 前端 → 状态与下钻（W048–W060）

**工程/状态**（W048–W050）：Vite/React 路由、URL 状态、`useApi`。

**页面**（W051–W055）：总览、城市门店、风险、门店详情、商品五页。

**B-01**（W056）：共现门槛隐藏 92/117 → 五态文案。

**返回/安全/联动**（W057–W059）：

- `returnTo` + 浏览器历史；
- `safeReturnTo` 8 层校验；
- 精确/至少切换、冲突降级、空 domains 400、选中行高亮。

**因果**：到 W059，用户才能“筛选→下钻→返回→继续筛选”而不丢状态。

---

## 第九段：测试 → 验收 → 交付（W061–W066）

**测试**（W061–W064）：101 pytest、23 vitest、56 E2E。

**整体回归**（W065）：build、25/25 SHA、21 项边界探针、性能采样。

**交付**（W066）：本地 5173/8000/4173、启动说明、展示路径。

**因果**：测试锁定冻结数字；E2E 锁定真实交互；冻结校验锁定数据版本；运行说明让项目可被他人启动。

---

## 整条链的五个“转折点”

1. **没有数据 → 缩减需求**（W002→W008）：项目从“六模块”变成“四块”。
2. **sale_amount 不是金额**（W007）：项目从“金额分析”变成“销量分析”。
3. **冻结**（W039）：项目从“分析报告”变成“可展示的事实”。
4. **BI 只读**（W041–W047）：项目从“报告”变成“查询层”。
5. **状态与返回**（W057–W059）：项目从“能看”变成“能用”。

## 如果没有某一环，会发生什么

| 缺少 | 后果 |
|---|---|
| W005 哈希校验 | 可能基于损坏文件分析，结论不可信 |
| W007 口径纠正 | 全项目金额叙事错误 |
| W010 契约 | 数据变化时分析静默失效 |
| W011 只加列清洗 | 原始证据丢失，无法追溯 |
| W014 派生表 | 每次分析扫 4.5M 行，慢且易口径不一 |
| W018 稳健 z | 异常日被长尾稀释 |
| W024 分母修正 | 品类效率结论错误 |
| W031 行序修正 | bootstrap CI 不可复现 |
| W033 池化率 | 整体缺货率偏高 |
| W038 n<20 整改 | 小样本被当结论 |
| W039 冻结 | BI 数字漂移 |
| W043 冻结校验 | 篡改文件也能启动 |
| W045 后端抑制 | 前端可能绕过 n<20 |
| W049 URL 状态 | 刷新/分享丢筛选 |
| W057 返回机制 | 多级下钻回不去 |
| W059 路径校验 | returnTo 可被穿越 |
| W065 整体回归 | 各阶段通过但组合后失效 |

## 结论

项目的研发不是“先设计完整架构，再按图施工”。

它是：

```
数据约束 → 需求裁剪 → 地基 → 分析 → 审计 → 修正
  → 冻结 → 只读 API → 页面 → 状态/安全 → 回归 → 交付
```

每一步都在解决上一步暴露的问题；每一个“最终方案”都是当时约束下的可接受选择。
