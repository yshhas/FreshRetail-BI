# 06 BI 后端与只读接口（W041–W047）

> 这一阶段把冻结数据变成只读 API。核心代码：`bi/src/bi_api/db.py`、`freeze.py`、`models.py`、`service.py`、`main.py`。
> 原则：BI 不算指标，只查冻结结果；前端不做聚合，统计与抑制都在后端。

## W041 BI 产品设计：只读定位、角色与页面

### 工作背景

P4 冻结后，项目面临选择：继续做报告，还是做可交互的 BI？

### 输入

P1–P4 结果、09 设计方案、运行环境（单机 Windows）。

### 实际步骤

1. 明确 BI 定位：只读展示与查询层，不是第二套分析系统；
2. 定义 6 类角色：经营负责人、城市/区域运营、门店运营、商品/品类运营、数据分析师、数据管理员；
3. 规划 9 个页面；
4. 确定技术栈：React + TypeScript + ECharts + FastAPI + DuckDB；
5. 明确非目标：不做金额、用户、实时、AI、评分、排名。

### 核心原理

BI 的价值是“让已验收的分析结果可查、可筛选、可下钻”，不是“重新算一遍”。如果重算，就会出现两套口径。

### 产物

`09_BI产品需求与技术架构设计方案.md`。

### 运行实例

设计中的典型问题：

- 经营负责人：哪里风险最多？
- 城市运营：C03 的门店效率分布如何？
- 商品运营：哪些风险 SKU 覆盖最广？
- 数据分析师：这个数字的口径和样本量是什么？

### 遇到的问题

设计规划了 `/explore`、`/methodology`、React Query、Zustand、Docker；实际未全部落地。这些差异后来被明确记录，而不是假装完成。

### 验证

设计与实际路由/代码对照（W048）。

### 下游

W042 视图层。

## W042 DuckDB 只读视图（22 → 25）

### 工作背景

冻结结果是 CSV/Parquet 文件，API 不能直接读文件拼 SQL。需要一层稳定的视图。

### 输入

`data/derived/*.parquet`、`data/analysis/p2|p3|p3d|p4/*.csv`。

### 实际步骤

1. `ReadOnlyDB._create_views` 建 22 个视图；
2. BI-2-A 增加 3 个商品视图，共 25 个；
3. `v_store` 三表 LEFT JOIN，`COALESCE` 生成 `diagnosis_status`；
4. `v_risk_at_least` 过滤 `domain_a <> domain_b`，保留 10 对；
5. 所有视图只读，不物化。

### 核心原理

视图把“文件路径 + CSV 解析 + 字段命名”封装起来，`service.py` 只面对稳定的表名与字段名。

### 产物（关键视图）

| 视图 | 来源 | 行数 |
|---|---|---:|
| `v_store` | P4-A + P4-B + not_applicable | 898 |
| `v_city` | P3-A + P3-D 城市 | 18 |
| `v_risk_exact` | P4-B 精确组合 | 16 |
| `v_risk_at_least` | P3-D d8b 去对角线 | 10 |
| `v_sku` / `v_sku_risk` | P2 | 865 / 117 |
| `v_store_sku` | P4-C incidence | 50,000 |
| `v_sku_pairs` | P4-C 共现 | 1,237 |
| `v_store_groups` | 四象限×结构群 | 16 |

### 运行实例（关键 SQL）

```python
self._view("v_store", f"""
    SELECT a.*,
           COALESCE(b.diagnosis_status, n.diagnosis_status, '不适用') AS diagnosis_status,
           b.domain_labels, b.exact_combo, b.structural_notes
    FROM {p4a} a
    LEFT JOIN {p4b} b USING (store_id)
    LEFT JOIN {p4n} n USING (store_id)
""")
```

### 遇到的问题

`v_store` 必须保留 10 家 SKU<10 门店，否则门店总数会从 898 变成 888，和页面文案对不上。

### 验证

`test_bi0_contracts.py::test_view_counts` 断言 25 个视图与行数。

## W043 冻结校验与启动失败

### 工作背景

如果 manifest 被改、文件被替换，API 仍然能启动，页面就会展示“未经校验”的数字。

### 输入

`freeze_manifest.json`（25 项）。

### 实际步骤

1. `_load_manifest_strict` 用 `object_pairs_hook` 拒绝重复 key；
2. 拒绝绝对路径与 `..`；
3. 校验 SHA-256 格式（64 位十六进制）；
4. 校验文件存在、SHA 一致、bytes 一致；
5. 校验 amendment `files_added` 与实际增量数一致；
6. `main.py` 的 `lifespan` 启动即调用，失败拒绝启动。

### 核心原理

冻结校验是“启动门槛”，不是“后台任务”。文件不对，服务就不应该起来。

### 产物

`freeze.py`；`main.py:20-27`。

### 运行实例（本轮）

```
{'version': 'p1-p4-freeze-2026-11-08',
 'contract_version': 'bi0-contract-v2',
 'files_total': 25, 'checked': 25, 'amendments': 1}
```

### 遇到的问题

BI-0 v2 增加 3 个商品文件时，不能修改原 22 项；只能追加，并保持 `data_version` 不变。

### 验证

`test_bi0_contracts.py` 覆盖重复 key、路径穿越、SHA 格式、篡改、缺失、bytes；9 个失败分支全部触发。

## W044 API 契约：Envelope、Meta、分页与白名单

### 工作背景

前端需要稳定的响应结构；后端需要统一参数校验与错误处理。

### 输入

`models.py` 的 `Envelope`、`Meta`、各 Row 模型。

### 实际步骤

1. 所有响应统一 `{data, meta, warnings}`；
2. `Meta` 包含 `n`、`period`、`data_version`、`sample_scope`、`suppressed`、`definitions`、`display_window`；
3. 分页 `page>=1`、`page_size<=200`；
4. 排序/风险域/组合定义用 `Literal` 或白名单；
5. `ValueError → 400`，缺失 → 404；
6. CORS 只允许本地 5173、仅 GET。

### 核心原理

统一 envelope 让前端只需一套解析；`meta` 让“样本量/口径/版本/是否抑制”随数据返回，避免用户只看数组。

### 产物

`models.py`、`main.py` 的路由与参数。

### 运行实例（真实响应）

```json
{
  "data": [{"store_id": 0, "city_id": 0, "total_index": 7181.57, ...}],
  "meta": {"n": 888, "period": "2024-03-28/2024-06-25",
           "data_version": "p1-p4-freeze-2026-11-08",
           "sample_scope": "risk", "suppressed": false},
  "warnings": []
}
```

### 遇到的问题

`trend` 接口只有在 `start` 与 `end` 同时存在时才过滤；单侧参数会被静默忽略，这是一个已知小缺口。

### 验证

`test_bi0_api.py::test_health_and_meta`、`test_kpis_trend_cities`；`test_bi2_products.py::test_whitelists_and_invalid_params`。

### 下游

全部页面。

## W045 门店 API：筛选、详情、分组抑制与导出

### 工作背景

BI-1 的第一批页面全部围绕门店：总览、城市与门店、风险、门店详情。

### 输入

`v_store`、`v_store_groups`。

### 实际步骤

1. `_store_where` 处理城市、象限、结构群、风险域、精确组合、至少组合、样本范围；
2. `stores` 排序白名单，非法回退 `store_id`；分页；
3. `store_detail` 按 ID 返回；
4. `store_groups` 在 n<20 时把三个统计字段置 None，并 `suppressed=true`；
5. `export_stores_csv` 导出 23 列，前 4 行注释。

### 核心原理

筛选必须参数化；小样本必须在后端抑制，不能指望前端。

### 产物

`service.py:147-238`、`export_stores_csv`。

### 运行实例（真实请求）

`GET /api/v1/stores?sample_scope=risk&page_size=2` → `meta.n=888`，前两条为 store 0、store 1。

`GET /api/v1/stores?exact_combo=缺货+高零销&sample_scope=risk&page_size=2` → `meta.n=38`，第一条 store 70，`exact_combo="缺货+高零销"`。

`GET /api/v1/stores?domains=stockout_domain,R4&sample_scope=risk&page_size=2` → `meta.n=56`。

### 遇到的问题

`exact_combo` 必须先与 `v_risk_exact` 全集比对，否则任意字符串都会变成“0 家”，用户无法区分“拼错”和“真的没有”。

### 验证

`test_bi2c_stores.py` 8 个测试；`test_bi0_api.py::test_stores_filters_and_detail`、`test_groups_suppressed`。

### 下游

## W046 风险 API：summary 与 combinations

### 工作背景

风险页需要五个域计数、多风险门店数、精确/至少组合。

### 输入

`v_risk_domain`、`v_store_profile`、`v_risk_exact`、`v_risk_at_least`。

### 实际步骤

1. `risk_summary` 统计五域计数、R7/R8 结构提示、`multi_risk`；
2. `risk_combinations('exact')` 读冻结 rank；
3. `risk_combinations('at_least')` 拼接 `domain_a+domain_b`，服务端按门店数赋 rank；
4. 返回 `meta.n` 与 `definitions=["D17"]`。

### 核心原理

精确组合有冻结 rank，至少组合没有；服务端临时赋 rank 只用于展示，不是冻结字段。

### 产物

`service.py:581-610`。

### 运行实例（真实响应）

`GET /api/v1/risk/combinations?definition=at_least`：

| 组合 | 门店数 | rank |
|---|---:|---:|
| 缺货+高零销 | 56 | 1 |
| 持续低销+高波动 | 44 | 2 |
| 缺货+高波动 | 31 | 3 |
| 缺货+高异常日 | 24 | 4 |
| 高零销+高波动 | 21 | 5 |
| 高波动+高异常日 | 18 | 6 |
| 高零销+高异常日 | 12 | 7 |
| 缺货+持续低销 | 9 | 8 |
| 持续低销+高零销 | 3 | 9 |
| 持续低销+高异常日 | 2 | 10 |

### 遇到的问题

至少组合的 rank 不是冻结值，若冻结表顺序变化，rank 可能与旧版本不同；这是已知小缺口。

### 验证

`test_bi0_contracts.py::test_risk_combinations_and_readonly`；`test_bi2c_c3_domains` 10/10 比对。

## W047 商品 API、契约 v2、性能与只读安全

### 工作背景

BI-2 需要五个商品端点和 3 个新视图；同时要保证只读安全与性能。

### 输入

`v_sku`、`v_sku_risk`、`v_store_sku`、`v_sku_pairs`、`v_category`、`v_sku_head_tail`、`v_category_penetration`。

### 实际步骤

1. 契约 v2：新增 3 个文件，25 项 SHA；
2. 新增 5 个商品端点；
3. `_product_where` 处理搜索（≤40）、类别、头尾、风险、覆盖区间；
4. `product_stores` 用 `COUNT(*) OVER()` 一次取分页与总数；
5. `product_pairs` 查 `v_sku_pairs`，返回统一 `definition`；
6. 只读安全：DuckDB 禁外部访问 + SQL 守卫 + `RLock`。

### 核心原理

商品覆盖门店接口原本 462ms，因为两次扫描；窗口函数把总数带在同一次查询里，P95 降到约 216ms。

### 产物

`service.py:430-578`；`v_store_sku`（50,000）、`v_sku_head_tail`（2）、`v_category_penetration`（32）。

### 运行实例（真实响应）

`GET /api/v1/products/4`：

- `product_code=P0005`；
- `store_count=783`；
- `total_index=183,265.3`；
- `risk_flag_count=1`；
- `risk_flags` 四项定义随响应返回。

`GET /api/v1/products/4/stores?page_size=2` → `meta.n=783`。

`GET /api/v1/products/4/pairs?limit=3` → `meta.n=110`，第一条 P0601 / 440 店 / 48.998%。

### 遇到的问题

B-01：详情页只展示 ≥20 店的共现，导致 92/117 个风险 SKU 页面空白；修正见 W056。

### 验证

`test_bi2_products.py` 10 个测试；`test_bi0_api.py::test_concurrent_reads_are_safe`（5 线程）；`test_bi0_contracts.py::test_duckdb_external_access_is_blocked`。

W055 商品五页、W056 共现五态。
