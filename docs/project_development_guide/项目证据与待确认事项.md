## 三、B 级证据（工程推断）

以下内容有实现与上下文依据，但没有开发者自述，属于“工程还原”：

1. **为什么选 Huber 而不是 OLS**：代码同时跑 OLS/RLM/QuantReg，说明做过对照；但文档没有记录选择讨论。
2. **为什么用 URL 而不是全局状态**：C-0 有方案对比，但没有记录实际讨论。
3. **为什么自研 `useApi`**：设计建议 React Query/Zustand，实际未用；推断是为了减少依赖。
4. **“先数据后展示”的架构动机**：由阶段顺序推断。
5. **生产可靠性判断**：由无鉴权/无 Docker/单连接推断。
6. **“审计驱动开发”的判断**：由问题发现方式归纳。

这些内容在正文中标注为“推断/合理推断”。

## 九、仍然存在的风险

1. **无 Git**：无法用提交记录验证历史；本套文档的时间线是逻辑重建。
2. **硬编码数字多**：898/888/865/117/35/43/16/10/38/56 散落前后端；重冻结会漂移。
3. **单连接 + RLock**：查询串行，多用户会排队。
4. **无鉴权/限流**：只能本地。
5. **无 CI**：测试靠手动。
6. **依赖漏洞 9 项**：延后升级。
7. **CSV 导出**：不支持组合筛选，无公式注入转义。
8. **R-01**：`summarizePairs` 未校验字段有限性/唯一性。
9. **包体积**：JS 1.29MB，未做代码分割。
10. **文档数字不一致**：见第五节。

## 十、如何使用本文件

- 写报告/答辩时，引用“A 级证据”中的文件与数字；
- 解释设计原因时，明确说“这是工程推断（B）”；
- 遇到无法确认的问题，直接引用“C 级证据”，不要补故事；
- 发现文档矛盾时，按第五节的处理方式说明，而不是二选一硬写。
