## W009 目录分层：raw / derived / logs

### 工作背景

W008 之后，项目确定只做销量、商品、区域、诊断。要做这些分析，首先得决定数据放在哪里、哪些能改、哪些不能改。

### 输入

原始 `train.parquet`、`eval.parquet`；尚无派生目录。

### 实际步骤

1. 设定 `data/raw/freshretailnet50k/` 为原始文件目录，只读；
2. 设定 `data/derived/` 为清洗与聚合产物目录，可重建；
3. 设定 `logs/` 为运行日志目录；
4. 在 `config.py` 中固化路径常量。

### 核心原理

分层的目的不是“好看”，而是保证**可追溯**：

- raw 不可变 → 任何结果都能回溯到源头；
- derived 可重建 → 不怕误删/改坏；
- logs 记录每次运行 → 知道哪次产出了什么。

### 产物

`config.py` 中的 `DATA_DIR`、`RAW_DIR`、`DERIVED_DIR`、`LOG_DIR`、`TRAIN_PATH`、`EVAL_PATH`。

### 运行实例

```
data/
  raw/freshretailnet50k/train.parquet
  derived/clean_train.parquet
  derived/agg_daily.parquet
  ...
logs/
  pipeline_20261107T230354-dfc848.jsonl
```

### 遇到的问题

无。这是一个纯结构决定，但后续所有“可复现”都依赖它。

### 验证

`scripts/build_derived.py` 可以只读 raw、重写 derived；原始文件从未被修改。

## W010 数据契约：文件、数据帧与切分

### 工作背景

如果每次都靠“记得字段是什么”，分析代码会随着数据变化悄悄失效。需要把“数据承诺”写成代码。

### 输入

官方文件说明、19 个字段、`(dt, store_id, product_id)` 主键。

### 实际步骤

1. `check_file_metadata`：用 PyArrow 读行数、列数、字段顺序、Arrow 类型；
2. `check_frame`：检查空值、主键重复、日期连续、负值（discount 豁免）；
3. `check_split`：检查 train/eval 不重叠且间隔 1 天；
4. 任何不满足抛 `DataContractError`，中止流水线。

### 核心原理

契约是“输入必须满足的条件”。它把“数据坏了”从“分析结果奇怪”提前到“启动就失败”。

### 产物

`contracts.py` 的 `EXPECTED_SCHEMA`、`check_file_metadata`、`check_frame`、`check_split`。

### 运行实例（关键代码）

```python
EXPECTED_SCHEMA = {
    "city_id": "int64",
    "store_id": "int64",
    "product_id": "int64",
    "dt": "string",
    "sale_amount": "double",
    "hours_sale": "list<element: double>",
    "stock_hour6_22_cnt": "int32",
    "hours_stock_status": "list<element: int64>",
    ...
}
```

如果 `dt` 变成 `timestamp`，或者字段顺序变了，这里会直接报错。

### 遇到的问题

`discount` 允许 0 和 >1，因此负值检查要排除它；这不是漏洞，而是业务规则。

### 验证

`tests/test_contracts.py` 4 个测试：文件元数据、schema、时间切分、重叠报错。

### 下游

W011 清洗、W015 流水线。

## W011 清洗规则设计：R001–R012

### 工作背景

原始数据有 `discount=0`、`discount>1`、零销、缺货等语义问题。需要决定“怎么处理异常”。

### 输入

19 列原始数据、04 报告的质量结论。

### 实际步骤

1. 明确原则：只新增派生列，不覆盖原始列；不删行、不去重、不填补。
2. 为每个字段定义规则编号（R001–R012）。
3. 为每条规则写条件、动作、说明。
4. 把规则同时写成 SQL 表达式与 pandas 函数。

### 核心原理

清洗不是“修数据”，而是“给数据打标签”。原始值保留了，异常才可追溯；如果直接改掉，后面无法解释“为什么和原始数据对不上”。

### 产物

`cleaning.RULES`、`DERIVED_SQL`、`select_clean_sql`、`clean_frame`、`rules_payload`。

### 运行实例（真实规则）

| 规则 | 条件 | 派生列 |
|---|---|---|
| R001 | 总是 | `sales_index = sale_amount` |
| R002 | `discount=0` | `discount_missing` |
| R003 | `discount>1` | `discount_out_of_range` |
| R005 | `0<discount<1` | `promo_flag` |
| R008 | `stock_hour6_22_cnt>0` | `stockout_day_flag` |
| R009 | 总是 | `stockout_rate_6_22 = cnt/16` |
| R010 | `sale_amount=0` | `sales_zero_flag` |

### 遇到的问题

`discount=0` 到底是“0 折”还是“缺失”？项目选择标记为缺失，并在报告披露“促销率可能低估 0.36%”，而不是直接删除。

### 验证

`tests/test_cleaning.py` 4 个测试：原始列不变、派生旗标、越界折扣、规则可追溯。

### 下游

W012 双实现、W014 指标计算。

## W012 清洗的 SQL / pandas 双实现

### 工作背景

生产流水线用 DuckDB SQL 处理 4.5M 行；单元测试用小 pandas 样本。两套实现必须口径一致。

### 输入

`DERIVED_SQL` 与 `clean_frame`。

### 实际步骤

1. SQL 版：`select_clean_sql` 生成“原始 19 列 + 11 派生列”的 SELECT；
2. pandas 版：`clean_frame` 用布尔列完成同样转换；
3. 用同一批规则编号约束两套实现；
4. 测试只验证 pandas 版，生产使用 SQL 版，靠规则一致性保证结果一致。

### 核心原理

SQL 适合大数据，pandas 适合小样本测试。双实现的代价是“可能不一致”，收益是“测试快、生产快”。

### 产物

`cleaning.py:98-133`。

### 运行实例

```python
DERIVED_SQL = {
    "sales_index": "sale_amount",
    "discount_missing": "(discount = 0)",
    "promo_flag": "(discount > 0 AND discount < 1)",
    "stockout_day_flag": "(stock_hour6_22_cnt > 0)",
    "stockout_rate_6_22": "(stock_hour6_22_cnt / 16.0)",
    "sales_zero_flag": "(sale_amount = 0)",
}
```

```python
out["promo_flag"] = (out["discount"] > 0) & (out["discount"] < 1)
```

### 遇到的问题

`discount` 的边界（0、1、>1）容易在 SQL 与 pandas 中写出不同结果；因此规则表与测试必须逐条对应。

### 验证

测试覆盖 R002/R003/R005/R008/R009/R010 的关键边界。

### 下游

W014 指标计算依赖这些派生列。

## W013 DuckDB：内存连接、Parquet 视图与 COPY

### 工作背景

4.5M 行明细、1.08 亿行小时展开；需要快速聚合，但不想部署数据库服务。

### 输入

原始 Parquet、清洗后的 Parquet。

### 实际步骤

1. `duckdb.connect(":memory:")`；
2. `SET threads = 4`；
3. 用 `CREATE VIEW ... read_parquet(...)` 建原始/清洗视图；
4. 用 `COPY (SELECT ...) TO '...parquet' (FORMAT PARQUET, COMPRESSION ZSTD)` 写派生表；
5. `io.sql_path` 把 Windows 路径转正斜杠、转义单引号。

### 核心原理

DuckDB 是嵌入式列式分析引擎，能直接读 Parquet，不需要把数据导入数据库。视图不复制数据，查询时才扫描文件。

### 产物

`db.py` 的 `connect`、`create_raw_view`、`export_sql`、`build_clean_table`。

### 运行实例

```python
con.execute(f"CREATE OR REPLACE VIEW {name} AS SELECT * FROM read_parquet('{sql_path(path)}')")
```

```python
con.execute(f"COPY ({sql}) TO '{sql_path(out_path)}' (FORMAT PARQUET, COMPRESSION ZSTD)")
```

### 遇到的问题

Windows 反斜杠会被 SQL 当转义符；单引号会截断字符串。`sql_path` 解决这两个问题。

### 验证

流水线成功重建 `clean_train`（4,500,000 行）与 13 张派生表。

### 下游

W014 指标 SQL、W041 DuckDB 只读视图。

## W014 指标聚合层：12 个函数、13 张派生表

### 工作背景

P1–P4 需要日、门店、商品、城市、小时、诊断等多粒度聚合。如果每个分析脚本自己写 SQL，口径会散落。

### 输入

`clean_train` 视图。

### 实际步骤

1. 在 `metrics.py` 中实现 12 个聚合函数；
2. 每个函数输出一张 Parquet；
3. `pipeline.run()` 统一调用并落盘；
4. 额外生成异常日与健康度两张诊断表。

### 核心原理

指标层只做“聚合”，不做“解释”。它把 4.5M 行压缩成 90/898/865/18 等小表，供后续分析复用。

## W015 流水线编排与 JSONL 日志

### 工作背景

有了契约、清洗、指标，还需要一个“按顺序执行、失败就停、留下记录”的入口。

### 输入

`config`、`contracts`、`cleaning`、`db`、`metrics`、`io`、`RunLogger`。

### 实际步骤

1. `pipeline.run()` 依次执行：文件校验 → 元数据契约 → 原始质量 → 清洗表 → 派生表 → 元数据 JSON；
2. 每一步写日志事件；
3. 最后写 `_quality_report.json`；
4. 任何异常直接抛出，不吞掉。

### 核心原理

流水线是“可重复的实验记录”：同样的输入、同样的规则，必须得到同样的输出；日志记录每次运行的输入、输出、耗时。

### 产物

`pipeline.py`、`logging_utils.py`、`_cleaning_rules.json`、`_metric_catalog.json`、`_quality_report.json`。

### 运行实例

两次运行：

| 运行 | run_id | 耗时 |
|---|---|---:|
| 含哈希校验 | `20261107T230354-dfc848` | 15.94s |
| 跳过哈希 | `20261107T230457-0ad3fc` | 15.38s |

### 遇到的问题

没有 Git，日志成为唯一能证明“哪次运行产出了什么”的记录。

### 验证

`logs/` 下两份 JSONL 与 06 报告附录一致。
