## W034 P4-A 门店综合经营画像

### 工作背景

P1–P3 的结果分散在多张表里。用户想知道“这家门店怎么样”，需要同时翻 5 份报告。必须整合成一行一店。

### 输入

- `p3c/c1_store_structure.csv`（主表，898 行）；
- `p3d/d1_store_risk_base.csv`（R1–R8、domain_count、multi_risk）；
- `p3c/c8_cluster_assignments.csv`（G1–G4）。

### 实际步骤

1. 以 `c1` 为主表，按 `store_id` 左连接 P3-D 风险字段；
2. 左连接结构群 `cluster_k4`，映射为 G1–G4；
3. 生成 `profile_status`：`in_risk_sample=True` → 完整档案，否则基础档案（SKU<10）；
4. 选择 42 个字段输出；
5. 生成字段字典 `p4_a_field_dictionary.csv`。

### 核心原理

一行一店是 BI 门店详情的最小粒度。所有后续筛选（城市、象限、结构群、风险域）都可以在这张表上完成。

### 产物

- `p4_a_store_profile.csv`（898×42）；
- `p4_a_field_dictionary.csv`。

### 运行实例（真实行）

| store_id | city_id | profile_status | total_index | per_day_index | sku_count | quadrant | cluster | domain_count | multi_risk |
|---:|---:|---|---:|---:|---:|---|---|---:|---|
| 235 | 0 | 完整档案 | 17,510.53 | 194.561 | 162 | Q1 高规模·相对高效率 | G4 | 0 | False |

### 遇到的问题

P1 的 `rank` 不能放进档案，否则会被误用为门店排名/考核。

### 验证

`test_p4_diagnosis.py::test_p4_a_profile_scope` 断言 898 行、888 完整、10 基础。

### 下游

## W035 P4-B 诊断规则与精确组合

### 工作背景

有了门店档案，还需要回答“这家门店命中了什么风险、属于哪个组合”。

### 输入

`p3d/d1_store_risk_base.csv`（888 风险样本）。

### 实际步骤

1. `build_diagnosis` 只取 `in_risk_sample=True`；
2. 生成 `domain_labels`、`exact_combo`、`structural_notes`；
3. 生成 10 家不适用门店 `p4_b_not_applicable.csv`；
4. 生成“至少”门店-域对 `p4_b_store_pairs.csv`；
5. 只对 `domain_count>=2` 的门店按 `exact_combo` 分组，得到 16 种精确组合；
6. 生成规则库 `p4_b_rulebook.csv`（B0–S8）。

### 核心原理

精确组合 = 完整域集合相等；至少组合 = 同时命中两个域、允许其他域。精确组合各行可相加（合计 132），至少组合不可相加。

### 产物

- `p4_b_store_diagnosis.csv`（888×17）；
- `p4_b_not_applicable.csv`（10）；
- `p4_b_store_pairs.csv`（220）；
- `p4_b_exact_combinations.csv`（16）；
- `p4_b_domain_summary.csv`；
- `p4_b_rulebook.csv`。

### 运行实例（真实数据）

精确组合前两名：

| 组合 | 门店数 | 排名 |
|---|---:|---:|
| 缺货+高零销 | 38 | 1 |
| 持续低销+高波动 | 36 | 2 |

至少组合：
- 缺货+高零销 56；
- 持续低销+高波动 44；
- 缺货+高波动 31；
- 缺货+高异常日 24；
- 高零销+高波动 21。

规则库层次：

```
B0/B0X 适用性 → B1/B2/B3 按 domain_count 互斥 → S7/S8 独立结构提示
```

### 遇到的问题

规则库最初没有写执行层次，读者可能以为可以同时命中；后来补充了 B0–S8 的层次说明，但不改变任何命中结果。

### 验证

`test_p4_b_matches_p3d`、`test_p4_b_at_least_vs_exact` 断言 56/38；精确合计 132。

### 下游

BI 风险页（W053）、门店详情风险区（W054）。

## W036 P4-C 门店×SKU incidence 与共现

### 工作背景

商品 BI 需要回答“某门店有哪些 SKU、哪些是风险 SKU、哪些 SKU 经常同店出现”。

### 输入

`clean_train`、`p2/t1_sku_metrics`、`p2/t9_sku_risk_flags`、`p3c/c1`。

### 实际步骤

1. 用 DuckDB 聚合 `clean_train`，生成门店×SKU 的 50,000 行 incidence；
2. 每条记录包含 `days_present`、`observed_rows`、`total_index`、`zero_days`、`stockout_days`、`risk_flag_count`；
3. 汇总门店风险 SKU：`p4_c_store_sku_risk_summary`（898 行）；
4. 汇总 117 个风险 SKU 的覆盖分布；
5. 用 `itertools.combinations` 生成同店共同出现对，按 `stores_both` 排序；
6. 输出 `p4_c_sku_pair_cooccurrence`（1,237 对）。

### 核心原理

“同店共同出现”是观察期内两个 SKU 都进入同一门店，不要求同日、不要求同一订单。数据没有订单/购物篮，不能做“搭配”。

### 产物

| 文件 | 行数 |
|---|---:|
| `p4_c_store_sku_incidence.csv` | 50,000 |
| `p4_c_store_sku_risk_summary.csv` | 898 |
| `p4_c_flagged_sku_distribution.csv` | 117 |
| `p4_c_sku_pair_cooccurrence.csv` | 1,237 |

### 运行实例（真实行）

incidence 第一行：

| store_id | product_id | sku_display_code | days_present | observed_rows | total_index | zero_days | stockout_days | risk_flag_count |
|---:|---:|---|---:|---:|---:|---:|---:|---:|
| 0 | 4 | P0005 | 90 | 90 | 243.1 | 3 | 38 | 1 |

共现第一行：

| sku_a | sku_b | stores_both | share_stores_both |
|---|---|---:|---:|
| P0005 | P0601 | 440 | 0.489978 |

### 遇到的问题

“同时销售”这个词容易误导；后来统一改为“观察期内同店共同出现”，并明确不代表同日销售/购买搭配/因果。

### 验证

`test_p4_c_incidence_contract` 断言 50,000 行、主键唯一、`observed_rows` 合计 4,500,000、总指数 4,493,660.787；`test_p4_c_flagged_sku_reuse` 断言 117/35。

BI 商品详情（W055/W056）、门店 SKU 列表（W054）。

## W037 P4-C 四象限×结构群 16 格

### 工作背景

需要把门店分层（P3-B 四象限）与商品结构（P3-C 结构群）交叉，回答“某类门店的风险 SKU 占比高不高”。

### 实际步骤

1. 以 `p4_a_store_profile` 为基础，按 `quadrant`、`cluster` 分组；
2. 计算每组门店数、风险 SKU 中位数、风险 SKU 占比中位数、多风险率；
3. `sample_insufficient = stores < 20`；
4. 输出 `p4_c_quadrant_cluster_cross`（16 行）。

### 核心原理

交叉表能回答“同规模同效率、同结构的门店，风险是否集中”；但小样本单元格不能展示统计值。

### 产物

`p4_c_quadrant_cluster_cross.csv`（16 行）。

### 运行实例（真实行）

| quadrant | cluster | stores | n_flagged_median | share_flagged_median | multi_risk_rate | sample_insufficient |
|---|---|---:|---:|---:|---:|---|
| Q1 高规模·相对高效率 | G1 | 63 | 4.0 | 7.55% | 9.52% | False |
| Q1 高规模·相对高效率 | G2 | 11 | 6.0 | 10.91% | 9.09% | True |

5 个单元格 `stores<20`：Q1-G2(11)、Q2-G2(17)、Q3-G4(9)、Q4-G1(7) 等。

### 遇到的问题

第一版对这些小样本单元格仍展示中位数，违反“n<20 不比较”规则。

### 验证

`test_p4_c_pairs_and_cells` 断言 16 格、合计 888、`sample_insufficient` 标记。

## W038 P4 审计整改：n<20、文案、规则层次

### 工作背景

P4 完成后审计发现三个问题，都会影响读者理解。

### 输入

P4 报告、交叉表、规则库、共现表。

### 实际步骤

1. **P4-C-01**：n<20 单元格显示 `—`，不再展示中位数；
2. **P4-C-02**：统一“观察期内同店共同出现”文案，列明不代表什么；
3. **P4-B-01**：补规则执行层次（B0/B0X → B1/B2/B3 → S7/S8）。

### 核心原理

小样本不是“不能算”，而是“不能展示为可比较结论”；文案必须退到数据能支持的粒度。

### 产物

修改 `p4_diagnosis.py` 的展示字段与规则说明；P4 报告更新。

### 运行实例

Q1-G2 从“中位数 6.0”改为“—（n=11 < 20）”。

### 遇到的问题

后端原始值保留用于追溯，前端显示抑制；两者要成对测试。

### 验证

P4 测试从 54 增加到 62；`8 passed` 的 P4 专项；审计复核通过。

## W039 冻结设计：22 项 SHA 与 manifest

### 工作背景

P4 验收后，BI 需要读这些结果。如果结果被重跑覆盖，页面数字会漂移。必须把结果“锁住”。

### 输入

22 个核心结果文件（CSV/Parquet）。

### 实际步骤

1. 选定 22 个文件（后续扩到 25）；
2. 计算每个文件的 SHA-256 与字节数；
3. 写入 `bi/data/freeze_manifest.json`；
4. 记录 `version=p1-p4-freeze-2026-11-08`、`contract_version=bi0-contract-v2`；
5. BI 启动时 `verify_manifest()`，失败拒绝启动。

### 核心原理

冻结 = 不可变快照 + 哈希校验。它让 BI 展示的是“已验收的那一版值”，而不是“当前重算的值”。

### 产物

`freeze_manifest.json`；`freeze.py` 的 `verify_manifest`。

### 运行实例（manifest 关键字段）

```json
{
  "version": "p1-p4-freeze-2026-11-08",
  "contract_version": "bi0-contract-v2",
  "files": {
    "data/analysis/p4/p4_a_store_profile.csv": {
      "sha256": "...",
      "bytes": 123456
    }
  }
}
```

### 遇到的问题

冻结后新指标必须回分析层；测试里硬编码的数字如果与冻结值不一致会大面积失败。

### 验证

`bi/tests/test_bi0_contracts.py::test_freeze_manifest`；本轮 `verify_manifest()` 返回 25/25。

W040 P4 最终验收、BI-0（W043）。

## W040 P4 最终验收与 Feature Freeze

### 工作背景

整改完成后，需要确认 P4 可以冻结，作为 BI 的数据基础。

### 实际步骤

1. 跑 P4 全量测试（62 passed）；
2. 检查 898/888/10 的样本边界；
3. 检查 16 种精确组合、38/56；
4. 检查 50,000 incidence、1,237 对共现、16 格；
5. 出具最终验收报告，宣布 P4 Feature Freeze。

### 核心原理

验收不是“跑通”，而是“关键数字与冻结值一致、边界行为正确、已知限制明确”。

### 产物

`08_P4最终正式验收报告.md`；`p1-p4-freeze-2026-11-08`。

### 运行实例

P4 报告的关键数字：

- 门店档案 898 行；
- 完整档案 888、基础档案 10；
- 多风险 132（14.86%）；
- 精确组合 16、合计 132；
- “缺货+高零销” 精确 38 / 至少 56；
- incidence 50,000 行、共现 1,237 对。

### 遇到的问题

P3-D 报告中仍有“等待审查”的旧状态文字，由验收记录覆盖；属于已接受事项。

### 验证

最终验收报告“通过，P4 Feature Freeze”；25 项 manifest 后续校验通过。
