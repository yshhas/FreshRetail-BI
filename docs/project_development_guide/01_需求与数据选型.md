# 01 需求与数据选型（W001–W008）

> 这一阶段回答两个问题：**项目到底要做什么？手上有没有能支撑它的数据？**
> 所有结论都能在 01–05 报告与 `src/freshretail/config.py` 中找到依据。

---

## W001 项目定位与六模块设想

### 工作背景

项目最初不是“做一个 BI 网站”，而是“做一套完整的经营增长分析”。在没有数据约束之前，最自然的想法是覆盖企业经营的全部环节。

### 输入

只有项目名称与一个业务设想：中国数字零售与本地生活经营增长分析。

### 实际步骤

1. 把经营分析拆成六个模块：企业整体经营、用户价值、留存复购、商品经营、区域市场、诊断策略。
2. 为每个模块列出需要的指标：GMV、客单价、用户数、复购率、留存率、SKU 贡献、城市对比、缺货诊断等。
3. 推演这些指标需要什么数据：订单 ID、金额、时间、用户 ID、商品 ID、门店/城市。
4. 形成第一阶段的“数据前提”：一份订单级交易明细。

### 核心原理

经营分析链路的每一环都依赖上一环的数据粒度：

```
企业整体（订单/金额）
  → 用户价值（用户 ID）
  → 留存复购（用户 ID + 时间）
  → 商品（订单 + 商品）
  → 区域（门店/城市）
  → 诊断（以上全部）
```

没有订单，就无法把商品和金额关联；没有用户，就无法做复购；没有金额，就无法做 GMV。六模块不是六个独立功能，而是一条数据依赖链。

### 产物

- 六模块分析框架（01 报告 §6）；
- 所需字段清单；
- “订单级数据”这一硬前提。

### 运行实例

当时设想的典型问题：

> “某城市某类商品这个月销售额是多少？哪些用户复购了？哪些门店缺货最严重？”

回答它需要：订单表（订单 ID、金额、时间、门店）、订单明细（商品、数量）、用户表（用户 ID）。三者缺一不可。

### 遇到的问题

没有数据。项目手里只有“想做的分析”，没有“能做的数据”。

### 验证

01 报告 §6 明确写出：若坚持六模块不得缩减，方案 A 不足以支撑项目。

### 下游

这个设想直接引出了 W002：先去找数据，而不是先写代码。

## W002 第一轮候选数据集核验

### 工作背景

既然六模块需要订单级数据，第一步就是把能找到的公开候选逐一核验。

### 输入

候选清单：Olist、UCI Online Retail II、淘宝 UserBehavior、天猫订单报表、天池母婴、美团 TSL、CnOpenData、饿了么、TAOBAO-MM、CUMCM 2023 C 等。

### 实际步骤

1. 对每个候选记录规模、时间跨度、字段、粒度、许可、可获取性。
2. 检查是否具备五个核心要素：订单 ID、金额、时间、用户、商品。
3. 检查是否为中国场景、是否可公开作品集展示。
4. 对字段缺失或许可不清的候选直接淘汰。

### 核心原理

选数据集不是“越大越好”，而是“粒度匹配 + 字段可用 + 许可允许”。一个 1 亿行的点击数据集，如果不能回答“卖了多少钱”，对经营分析就是无用的。

### 产物

01 报告的候选核验表，记录了每个候选的规模、字段与淘汰原因。

### 运行实例（真实数字）

| 候选 | 规模/时间 | 关键缺陷 |
|---|---|---|
| Olist | 约 10 万订单、9 表、2016–2018 | 非中国 |
| UCI Online Retail II | 1,067,371 行×8 字段、2009–2011 | 单表、无类目、约 1/4 用户缺失 |
| 淘宝 UserBehavior | 987,994 用户、100,150,807 条、9 天 | 无金额、无订单、无地区 |
| 天猫订单报表 | 28,010 行×7 字段 | 无 user_id、无商品；链接失效 |
| 美团 TSL | 654,343 运单 | 无金额、无商品、无消费者 ID |
| 饿了么 | 1.28 亿样本、8 天 | 曝光样本非订单；金额为快照 |
| TAOBAO-MM | 8.79M 用户、99M 样本、139 GB | 仅点击标签，无金额 |
| CUMCM 2023 C | 4 附件、2020–2023 | 单店无地区；许可不明 |

### 遇到的问题

没有一个候选同时满足五要素 + 中国 + 可公开。

### 验证

01 报告 §8 的结论：没有任何一套数据能完整支持六模块中的任何一个模块。

### 下游

第一轮失败引出了 W003：是否放弃中国定位，用 Olist 做完整闭环？

## W003 核心数据集调研与 Olist 评估

### 工作背景

第一轮没有中国数据可用，项目面临第一次路线分叉：要不要退一步，用国外数据做完整闭环？

### 输入

Olist 数据集、UCI、以及第一轮的候选结论。

### 实际步骤

1. 深入评估 Olist 的 9 张表：订单、订单明细、支付、评价、商品、卖家、地理等。
2. 确认 Olist 可以支撑订单、金额、用户、商品、地域、评价的完整分析。
3. 对照项目名称中的“中国数字零售与本地生活”，判断场景是否匹配。
4. 记录结论：Olist 能闭环，但不是中国。

### 核心原理

“能分析”与“分析的是不是这个题目”是两件事。Olist 能回答“巴西电商怎么经营”，但不能回答“中国即时零售怎么经营”。

### 产物

02 报告 §G.1、§H.1：Olist 是“唯一可支撑完整经营诊断闭环”的候选，但中国定位无法满足。

### 运行实例

Olist 的表结构足以做：

- 订单金额、客单价、支付方式；
- 用户复购、RFM；
- 商品品类、卖家；
- 州/城市对比；
- 评价与履约。

这些正是六模块想要的。但它的城市、商品、用户全部是巴西场景。

### 遇到的问题

这是一个价值判断，不是技术判断：**保留“中国”，还是保留“完整”？**

### 验证

02 报告没有直接选 Olist，而是进入第三阶段继续找中国数据。这证明当时没有放弃中国定位。

### 下游

W004：第三阶段的中国数据源补充调研。

## W004 中国数据源补充与 FreshRetailNet-50K 选型

### 工作背景

项目决定再给“中国定位”一次机会，系统补充调研中国真实零售数据。

### 输入

中国公开数据源：电商、即时零售、竞赛、学术、商业数据平台。

### 实际步骤

1. 用八个维度筛选：中国真实、2021 后、交易粒度、四维字段、用户 ID、主外键、许可、非重复。
2. 发现 FreshRetailNet-50K（Dingdong-Inc）。
3. 核对其规模、时间、字段、许可。
4. 与第二阶段所有中国候选对比，确认它在四个维度同时胜出。

### 核心原理

一个可用的数据集必须同时满足“真实、够新、字段够、许可清”。任何一项不成立，项目就会在后续某一步卡住。

### 产物

03 报告 §C.1、§F、§I.1；最终选定 FreshRetailNet-50K。

### 运行实例（真实数字）

| 项 | 值 |
|---|---:|
| 总行数 | 4.85M（train 4.5M + eval 0.35M） |
| 序列 | 50,000 条门店×SKU |
| 门店 / 城市 / SKU | 898 / 18 / 865 |
| 时间 | 2024-03-28 ~ 2024-06-25（90 天） |
| 字段 | 19 列：销量、小时销量、缺货、折扣、天气等 |
| 许可 | CC BY 4.0 |

### 遇到的问题

它没有金额、没有用户、没有订单，只有 90 天。这是选它必须接受的代价。

### 验证

03 报告把它列为“核心源”；04 阶段实际下载并核验成功。

### 下游

W005：下载与哈希校验。

## W005 数据获取与哈希校验

### 工作背景

选定数据集后，第一件事不是分析，而是确认“下载到的文件和官方发布的是同一份”。

### 输入

官方 Hugging Face LFS manifest 中的文件大小与 SHA-256；本地通过 hf-mirror 下载的 `train.parquet`、`eval.parquet`。

### 实际步骤

1. 读取本地文件大小。
2. 计算 SHA-256。
3. 与官方 manifest 逐项比对。
4. 不一致则中止。

### 核心原理

SHA-256 是文件指纹：内容改动一个字节，指纹就完全不同。它能证明文件完整性，但不能证明“内容正确”。

### 产物

`io.verify_file`、`config.EXPECTED_FILES`，以及 04 报告的核验记录。

### 运行实例（真实值）

| 文件 | 大小 | SHA-256 |
|---|---:|---|
| `train.parquet` | 106,436,287 B | `6706832d…de5a3d` |
| `eval.parquet` | 8,440,124 B | `1b118840…995e960e` |

两者均与官方 LFS 记录一致。

### 遇到的问题

本机无法直连 huggingface.co，改用 hf-mirror；因此更需要哈希校验来排除镜像差异。

### 验证

`tests/test_contracts.py::test_file_metadata_matches_manifest` 校验行数/列数/字段顺序。

### 下游

W006：数据质量核验。

## W006 数据质量核验：结构、异常与长尾

### 工作背景

文件一致不代表数据可用。需要确认行数、字段、主键、空值、负值、日期、分布。

### 输入

`train.parquet`（4,500,000 行 × 19 列）。

### 实际步骤

1. 用 PyArrow 读元数据：行数、列数、字段名、Arrow 类型。
2. 用 DuckDB 建原始视图，检查主键重复、空值、负值、日期范围与连续性。
3. 检查 `hours_sale` 与 `sale_amount` 是否自洽。
4. 统计 `discount`、`sale_amount` 的异常与分布。
5. 检查 train/eval 是否时间重叠。

### 核心原理

数据质量检查不是“看一眼”，而是把可验证的约束写成检查：

- 主键唯一；
- 无空值/负值；
- 日期连续；
- 数组字段与汇总字段自洽；
- train/eval 不重叠且紧邻。

### 产物

`contracts.py`、`pipeline._raw_checks`、04 报告 §3–§6。

### 运行实例（真实结果）

| 检查 | 结果 |
|---|---|
| 行数 / 列数 | 4,500,000 / 19 |
| 主键重复 | 0 |
| 空值 | 0 |
| 负值 | 0 |
| 日期 | 2024-03-28 ~ 2024-06-25，90 天连续 |
| `hours_sale` vs `sale_amount` | 最大误差 1.4e-14 |
| `discount=0` | 16,039 行（0.36%） |
| `discount>1` | 34 行 |
| `sale_amount=0` | 200,760 行（4.46%），76.62% 伴随缺货 |
| 分布 | 中位 0.7、均值 0.999、最大 44.9、偏度 8.47 |

### 遇到的问题

- `discount=0` 与官方“1.0=无折扣”冲突；
- 零销与缺货高度耦合；
- 长尾分布让均值/标准差不可靠。

### 验证

06 阶段把这些检查写成 4 个契约测试 + 4 个清洗测试。

### 下游

W007：字段口径纠正；W011：清洗规则。

## W007 口径纠正：`sale_amount` 不是金额

### 工作背景

第三阶段曾把 `sale_amount` 当作“销售额”，并推测单位可能是“万元”。如果这个理解错了，整个项目叙事都会错。

### 输入

官方数据说明、`sale_amount` 分布、`hours_sale` 自洽性。

### 实际步骤

1. 核对官方说明：`sale_amount` 是“全局归一化后的销售数量（再乘特定系数）”。
2. 用数据验证：`hours_sale` 合计与 `sale_amount` 完全一致，说明它是数量聚合，不是金额。
3. 确认没有价格、支付、订单字段可以反推金额。
4. 全项目改用“归一化销量指数”。

### 核心原理

字段名不可信。单位必须由官方定义 + 数据内部一致性 + 业务常识三方交叉确认。

### 产物

- `config.SALES_INDEX_NOTE`；
- 05 报告 §10.3 的禁止词清单；
- 后续所有报告/页面禁用“销售额/GMV/客单价”。

### 运行实例

`P0005` 的 `total_index=183,265.3`，是销量指数合计，不是 18.3 万元销售额。它的 `total_share=4.08%` 是销量份额，不是金额份额。

### 遇到的问题

第三阶段的“万元”推测必须公开作废；已经写过的金额叙事要全部改写。

### 验证

`hours_sale` 与 `sale_amount` 最大误差 1.4e-14；04 报告附录 B 明确以 04 为准。

### 下游

W008：需求裁剪；后续所有指标只能用“销量指数”。

## W008 需求裁剪：六模块 → 四块

### 工作背景

口径确认后，项目必须决定：没有金额、没有用户、没有订单，六模块还能留下什么？

### 输入

04 的能力矩阵、05 的方案调整、09 的非目标清单。

### 实际步骤

1. 保留并重定义：销量经营、商品经营、区域市场、运营诊断。
2. 删除：GMV、销售额、客单价、订单量、退款率、支付/利润、用户数、新老客、RFM、复购、留存、Cohort、流失预测。
3. 降级：模块二/三改为“数据能力边界”说明。
4. 写入禁止词清单与报告边界。

### 核心原理

需求不是“想做什么”，而是“能被数据验证什么”。不能验证的需求，写出来就是叙事。

### 产物

05 报告 §2.2、§10.3；项目正式从“金额经营分析”转为“销量经营分析”。

### 运行实例

| 原需求 | 处置 | 原因 |
|---|---|---|
| GMV/销售额 | 删除 | 无金额 |
| 客单价 | 删除 | 无订单 |
| 复购/留存 | 删除 | 无用户 ID |
| 商品经营 | 保留 | 有 SKU/销量 |
| 区域对比 | 保留 | 有城市/门店 |
| 诊断 | 保留但禁因果 | 有缺货/风险字段 |

### 遇到的问题

删功能比加功能难。项目需要接受“看起来不完整”，换取“每个数字都真实”。

### 验证

05 报告与 09 设计方案的“非目标”一致；后续所有阶段没有出现金额指标。

### 下游

W009：为四块分析搭建数据基础设施。
