# 第五章 那些真正改变项目的困难

## 5.1 这一章为什么单独存在

如果只看最终代码，很容易产生一种错觉：这个项目是一路顺着设计走下来的。

实际上，项目中途发生过多次“原方案不够用”的时刻。有些是数据层面的，有些是指标层面的，有些是交互层面的，有些是安全层面的。

这一章不讲“功能怎么做”，只讲“哪些问题逼着项目改变”。

这些问题有一个共同点：**它们都不是“程序跑不起来”，而是“程序跑起来了，但结果是错的/会被误解的/会被绕过的”。**

这类问题比报错更难发现，也更值得记录。

---

## 5.2 第一次：当“单店日均”的分母不是门店-日

### 5.2.1 问题是怎么出现的

P2 要做品类对比。报告里有一个指标叫“单店日均销量指数”，用来回答“哪个类目的经营效率更高”。

这个指标看起来很普通：累计销量指数除以门店数/天数。

审计在做独立复算时，随手拿 C05 这个类目核对了一下：

- 报告值：1.184；
- 按门店-日口径重算：14.545。

差了十倍以上。

再核对 C22：

- 报告值：1.795；
- 重算：6.083。

S029：

- 报告值：1.319；
- 重算：12.681。

### 5.2.2 根因

`per_series_day` 的分母是 `COUNT(*)`，也就是“SKU-门店-日”的行数，不是“门店-日”的去重数。

但字段名、表头、报告解读都写成“单店日均”。

这不是计算错误，而是**命名错误**。指标本身是“单序列日均”，只是被叫成了“单店日均”。

### 5.2.3 为什么原来的方案不够用

如果只是把数字改掉，会丢失一个有用指标：单序列日均本身是有意义的（它衡量一个 SKU 在单店的日均销量）。

如果直接把名字改成“单序列日均”，报告里的图表和结论又要全部重做。

### 5.2.4 最终方案

项目选择“改名 + 新增”：

- 原指标改名 `category_sku_store_day_avg`；
- 新增 `category_store_day_avg = 累计指数 / COUNT(DISTINCT store_id, dt)`；
- 新增 f11/f12 两张图；
- 报告同步解释两个口径。

### 5.2.5 验证与影响

修正后 29 passed，已通过的数字没有变化。

这件事影响很大：它让项目意识到，“日均”这个词必须带分母。后来 BI 里所有“单店日均”“单序列日均”都明确写口径。

## 5.3 第二次：当 R² 不是 R²

### 5.3.1 问题是怎么出现的

P3-B 用稳健回归拟合“规模 → 效率”。报告里写了一个 `R²_weighted=0.1194611254`。

读者看到 R²，自然会理解为“模型解释了 11.9% 的变异”。

审计指出：它不是标准 R²，而是“基于 RLM 最终权重的样本内加权拟合指数”。

### 5.3.2 根因

稳健回归的权重不是 1，不能直接用普通 R² 公式。项目实现了一个加权版本，但沿用了 R² 的名字。

### 5.3.3 为什么原来的方案不够用

0.119 这个数字本身说明模型很弱。如果叫“R²”，读者会以为“虽然弱，但至少是一个标准拟合优度”；叫“加权拟合指数”，读者才知道“这不是标准指标，只能作探索性参考”。

更麻烦的是，报告里还有“≥30 门槛一致率 82.23%”，只在 681 家交集上成立，另外 207 家没有参与。这个“82.23%”也被写成了整体一致率。

### 5.3.4 最终方案

- 改名为“加权拟合指数”；
- 结论降级为“弱拟合、仅探索性分层”；
- 门槛表补“交集/未参与”列；
- `ok_with_caution` 的表述改为更保守。

### 5.3.5 验证与影响

四象限结果 261/183/183/261 没有变，但报告的可信度提高了。

这件事的教训是：**自定义统计量不能借用标准名称。** 名字会决定读者对结论强度的判断。

## 5.4 第三次：当行序改变了置信区间

### 5.4.1 问题是怎么出现的

P3-C 用 bootstrap 计算相关系数的置信区间。

审计把同一份数据换了一个行顺序，重新跑了一遍，发现 CI 变了：

- 原 CI：−0.798734 ~ −0.734246；
- 按 `store_id` 排序后：−0.801941 ~ −0.735777。

### 5.4.2 根因

bootstrap 是有放回抽样。抽样按数组顺序进行，输入行序不同，抽到的样本就不同。

固定 `seed=42` 只能保证“同一行序下可复现”，不能保证“不同行序下可复现”。

### 5.4.3 为什么原来的方案不够用

项目一直以为“固定 seed 就可复现”。这个假设在行序稳定的情况下成立，但数据合并、排序、过滤都可能改变行序。

### 5.4.4 最终方案

- `_spearman_ci` 先按 `store_id` 排序，再抽样；
- 新增“行序不变性”测试；
- 同时修正了报告图片路径断链、抽样与典型店重叠的问题。

### 5.4.5 验证与影响

测试从 44 增加到 45，CI 变为 −0.801941 ~ −0.735777。

这件事让项目形成了一个习惯：**任何随机过程，先排序，再抽样。**

## 5.5 第四次：当整体缺货率被“二次加权”

### 5.5.1 问题是怎么出现的

P3-D 报告写整体缺货率 0.4434 / 0.2027。

审计拿 4.5M 行明细复算，发现正确池化值应该是 0.442668 / 0.198771。

### 5.5.2 根因

原来的算法是：

1. 先算每个城市的缺货率；
2. 再按城市门店数加权平均。

这等于让门店数多的城市被重复加权。它不是“总缺货小时 / 总小时”，而是“城市率的加权平均”。

### 5.5.3 为什么原来的方案不够用

“整体缺货率”最自然的解释是“所有 SKU-日里有多少出现过缺货”。这个值必须能在明细上对账。

城市加权率回答的是另一个问题：“如果按城市规模加权，平均城市缺货率是多少？”它不是整体率。

### 5.5.4 最终方案

- 改为池化率：`Σ分子 / Σ分母`；
- SKU-日：1,992,006 / 4,500,000 = 0.442668；
- 小时槽位：14,311,536 / 72,000,000 = 0.198771；
- 旧值只保留在否定句里，说明它不是整体率。

### 5.5.5 验证与影响

修正后 54 passed。P3 整体验收采用新值。

这件事的教训是：**率的聚合有三种，池化、简单平均、加权平均。写“整体率”必须说明是哪一种。**

## 5.6 第五次：当 54 家低销门店“消失”

### 5.6.1 问题是怎么出现的

P3-D 在做 R3（持续低销）时，审计发现主样本里有 54 家门店的真实连续低销天数是 1–6 天，但在 `max_low_run_days` 字段里显示为 0。

### 5.6.2 根因

P1 的 `sustained_low` 只把“连续低销 ≥7 天”的门店写进 `t11`。P3-B 合并时，对未达标门店 `fillna(0)`。

于是“真实 1–6 天”和“完全没有低销”被合并成了同一个 0。

### 5.6.3 为什么原来的方案不够用

R3 的二元判断（≥7 天）没有错，但后续分析（比如“低销天数与波动的相关性”）需要真实天数。缺失被当成 0，会扭曲相关性。

### 5.6.4 最终方案

P3-D 没有改 P1/P3-B 的历史文件，而是：

- 按 P1 原规则，从 `agg_store_day.parquet` 独立复算真实最长连续低销天数；
- 新字段 `low_run_max_days`；
- R3 仍用 P1 的二元定义，保持命中 90 不变；
- `low_run_max_days` 只用于 F5 和相关分析。

### 5.6.5 验证与影响

54 家门店恢复真实天数，R3 命中数不变。

这件事的教训是：**缺失 ≠ 0。** 管道里任何 `fillna(0)` 都要问一句：0 是真实值，还是“没有记录”？

## 5.7 第六次：当 92/117 个商品详情页变成空白

### 5.7.1 问题是怎么出现的

BI-2-B 的商品详情页有一个“同店共同出现”区块。

第一版只展示 `stores_both >= 20` 的对，并取前 20。

审计统计后发现：冻结数据里 117 个风险 SKU 中，有 92 个（78.6%）的详情页会显示“无共现”。

### 5.7.2 根因

这些 SKU 不是没有共现，而是所有共现对的 `stores_both` 都低于 20。

页面把“低于门槛被过滤”显示成了“没有数据”。

### 5.7.3 为什么原来的方案不够用

- 降低门槛会引入小样本误导；
- 展示全部会带来大量低质量记录；
- 只加一句提示，用户仍然看不到“到底有多少对”。

### 5.7.4 最终方案

- 请求 `limit=200`，尽量拿全；
- 新增 `summarizePairs`：只有 `rows.length === meta.n` 时才统计门槛；
- 页面区分五种状态：
  1. 真实 0 对；
  2. 全部低于门槛；
  3. 混合；
  4. 返回被截断；
  5. 元数据不可用。

### 5.7.5 验证与影响

以 P0001、P0052、P0005 为例：

- P0001：真实 0 对；
- P0052：5 对，全部低于门槛；
- P0005：110 对，24 对达标，展示 20 对，86 对低于门槛。

商品 E2E 17/17 通过。

这件事的教训是：**空态不是一种状态，而是五种状态。** “没有”和“被挡住”必须区分。

## 5.8 第七次：当 `returnTo` 可以被路径穿越

### 5.8.1 问题是怎么出现的

C-1 引入 `returnTo` 参数，允许详情页返回来源页。

审计构造了一个 URL：

```
/cities-stores/../risk
```

`new URL` 会把它规范化为 `/risk`。`/risk` 在白名单里，所以校验通过。

### 5.8.2 根因

校验发生在规范化之后。规范化已经把 `..` 消掉了，安全检查看到的是一个“合法路径”。

### 5.8.3 为什么原来的方案不够用

只检查 `url.pathname` 不够；只检查原始字符串里的 `..` 又会误伤查询参数（比如搜索词里包含 `..`）。

### 5.8.4 最终方案

`safeReturnTo` 改成多层校验：

1. 长度 ≤500；
2. 必须以单个 `/` 开头，拒绝 `//`；
3. 拒绝反斜杠；
4. 只取 `?`/`#` 之前的路径段，检查原始 `..`；
5. 最多解码 5 次，识别 `%2e%2e`、`%252e`、`%2f`、`%5c`；
6. `new URL` origin 校验；
7. 拒绝用户名/密码；
8. 白名单前缀；
9. 删除嵌套 `returnTo`。

### 5.8.5 验证与影响

新增 13 组单测 + 2 条 E2E，覆盖外链、协议相对、`javascript:`、5 层编码穿越。

这件事的教训是：**安全校验必须在规范化之前看到原始输入。**

## 5.9 第八次：当“返回”只能回一层

### 5.9.1 问题是怎么出现的

C-2 增加了“门店 → SKU → 商品详情”链路。

用户从城市页进入门店，再进入 SKU，再返回门店，再返回城市。

第一版用 `returnTo` 保存来源页。但 `returnTo` 只能保存“上一页 URL”，而上一页 URL 里可能还有更上层的 `returnTo`。

为了避免循环，`buildReturnTo` 会删除嵌套 `returnTo`。结果就是：从 SKU 返回门店后，再返回城市时，城市/风险条件丢了。

### 5.9.2 根因

`returnTo` 是“单层”的，无法表达多级链路。

### 5.9.3 为什么原来的方案不够用

- 保留嵌套 `returnTo` 会循环；
- 用全局状态保存导航栈又太复杂；
- 只靠 URL 参数无法恢复“上一页的上一页”。

### 5.9.4 最终方案

项目引入了浏览器历史：

- 新增 `BackLink` 组件；
- 如果存在 `returnTo` 且 `location.key !== 'default'`，用 `nav(-1)`；
- 否则跳到 `returnTo`；
- 两者都没有，回退默认页。

浏览器历史本身就是导航栈，不需要自己维护。

### 5.9.5 验证与影响

C-4 验证了“SKU→门店→城市”的完整链路，城市、风险域、样本范围、页码全部恢复。

这件事的教训是：**“返回”优先用历史；“可分享的返回”才用 URL 参数。两者结合，而不是二选一。**

## 5.10 第九次：当手工 URL 让页面自相矛盾

### 5.10.1 问题是怎么出现的

C-3 增加了 `domains` 参数（至少组合），与 `exact_combo`（精确组合）、`risk_domain`（单域）并存。

如果有人手工构造：

```
/risk?exact_combo=缺货+高零销&domains=stockout_domain,R4
```

页面会同时显示“精确组合”和“至少组合”，API 会因为互斥返回 400。

另一个问题是：`domains=`（空值）被静默忽略，URL 看起来在筛选，实际没有筛选。

### 5.10.2 根因

- 前端没有“冲突时以谁为准”的降级逻辑；
- 后端对空值的语义没有定义；
- 用户可编辑 URL，但页面假设 URL 总是合法的。

### 5.10.3 最终方案

前端：

- `comboConflict = exactCombo && domainPair`；
- 冲突时 `effectiveExactCombo=''`，以 `domains` 为准；
- 显示警告“URL 同时包含精确组合与至少组合参数…”；
- 模式切换时清空对侧参数。

后端：

- 空 `domains` 从“忽略”改为 400；
- 单域、重复域、R7/R8 继续 400；
- `domains` 与 `exact_combo`/`risk_domain` 互斥。

### 5.10.4 验证与影响

C-4 验证了冲突场景：显示 56 家、无错误；空 `domains` 返回 400。

这件事的教训是：**URL 是不可信输入。空字符串不是“没传”。**

## 5.11 第十次：当 462ms 成为商品详情的瓶颈

### 5.11.1 问题是怎么出现的

BI-2-A 的商品覆盖门店接口，P95 约 462ms，明显高于其他接口。

### 5.11.2 根因

先查分页数据，再单独查 `COUNT(*)`，两次扫描同一张大表（50,000 行 incidence + 898 门店 Join）。

### 5.11.3 最终方案

用窗口函数 `COUNT(*) OVER()`，一次扫描同时得到分页与总数。

### 5.11.4 影响

P95 从 462ms 降到约 216ms；本轮实测中位 187.5ms。

这件事的教训是：**分页接口优先“一次查询带总数”，不要为了代码简单做两次扫描。**

## 5.12 这些问题有什么共同点

把上面十个问题放在一起，会发现它们不是随机的。

### 共同点一：都不是“程序崩溃”

- 分母错了，程序照跑；
- R² 名字错了，报告照出；
- 行序变了，CI 照算；
- 二次加权了，数字照显示；
- `fillna(0)` 了，表照样完整；
- 共现被过滤了，页面照样渲染；
- 路径穿越了，页面照样跳转；
- 返回丢状态了，用户照样能点；
- 手工 URL 冲突了，页面照样打开；
- 接口慢了，功能照样可用。

这类问题不会让测试变红，只会让结果变错。

### 共同点二：都是“语义/口径/边界”问题

- “单店日均”是语义；
- “R²”是语义；
- “整体率”是口径；
- “缺失 vs 0”是边界；
- “没有 vs 被过滤”是边界；
- “返回”是边界；
- “URL 合法性”是边界。

技术实现本身不难，难的是“知道自己到底在算什么”。

### 共同点三：都是通过“独立复算/构造异常输入”发现的

- 分母错配：审计拿明细重算；
- R² 命名：审计对照定义；
- 行序 CI：审计换行序重跑；
- 二次加权：审计拿 4.5M 行对账；
- 54 家：审计检查上游字段；
- 92/117：审计统计被过滤数量；
- 路径穿越：审计构造恶意 URL；
- 多级返回：审计走完整链路；
- 手工冲突：审计手工拼参数；
- 462ms：性能测试。

这解释了为什么项目后来坚持“每个阶段都要独立审计”。不是不信任开发者，而是**这类问题只有换一个视角才能看见。**

---

## 5.13 这一章对后续的影响

这些问题直接塑造了 BI-2-C 的设计：

- 多级返回 → `BackLink` + 浏览器历史；
- 路径穿越 → `safeReturnTo` 多层校验；
- 手工参数冲突 → `effectiveExactCombo` + 警告；
- 空 `domains` → 400；
- 共现空白 → 五态文案；
- 性能 → `COUNT(*) OVER()`。

也塑造了项目的质量观：

- 测试通过不等于正确；
- 数字对得上不等于口径对；
- 页面能打开不等于状态正确；
- 审计不是“挑错”，而是“换一个视角复算”。
