# 第六章 最后一块拼图：跨页联动与“能回来的下钻”

## 6.1 进入这一章时的状态

第四章结束时，BI 已经有：

- 经营总览；
- 城市与门店；
- 经营风险；
- 门店详情；
- 商品总览、列表、风险、类别、详情。

页面能看，数据能查，但还不能“顺着问题往下走”。

比如用户在风险页看到“缺货+高零销”有 38 家门店，想点进去看其中一家；看完之后想回到风险页，最好还是那个组合、那个页码。

第一版的 BI 做不到这件事。返回会回到默认页，筛选丢失。

这就是 BI-2-C 要解决的问题：**跨页面联动与交互式下钻。**

---

## 6.2 C-0：先想清楚“状态放在哪里”

在写代码之前，项目先做了 C-0 方案设计。

C-0 没有直接讨论“按钮放哪里”，而是先回答一个更基础的问题：**筛选状态应该存在哪里？**

候选有三种：

1. 全局状态库（Redux/Zustand）；
2. React Context；
3. URL search params。

三种方案对比：

| 方案 | 刷新恢复 | 可分享 | 浏览器前进/后退 | 复杂度 |
|---|---|---|---|---|
| 全局状态库 | 否 | 否 | 否 | 中 |
| Context | 否 | 否 | 否 | 低 |
| URL | 是 | 是 | 是 | 低 |

项目选了 URL。

理由很直接：这个 BI 的核心使用场景是“筛选—下钻—返回—继续筛选”。如果刷新就丢筛选，或者不能把链接发给同事，体验会很差。

URL 还有一个天然优势：浏览器历史本身就是导航栈，不需要自己维护。

C-0 把后续工作拆成五块：

- C-1：URL 状态与返回；
- C-2：精确组合与门店 SKU；
- C-3：至少组合；
- C-4：整体验收；
- C-5：收尾（后来并入 C-4）。

这个拆分方式很工程化：先把“状态基础”做好，再做“业务筛选”，最后做“整体验收”。如果顺序反过来，先做组合筛选，后面再改状态模型，会大面积返工。

---

## 6.3 C-1：URL 状态与返回

C-1 做了三件事：

1. `useUrlFilters`：读写 URL；
2. `navigation.ts`：生成/校验 `returnTo`；
3. 在门店/商品详情页接入返回链接。

### 6.3.1 `useUrlFilters`

它提供三个方法：

```ts
get(key, fallback)
set(key, value)
patch(obj)
```

两个关键设计：

- 使用 `replace` 而不是 `push`，避免每次筛选都污染历史；
- 任何非 `page` 参数变化，都删除 `page`。

第二条很容易被忽略。如果用户在“风险门店”第 3 页，然后切换风险域，如果不删 page，新筛选结果可能只有 1 页，页面会显示空表。

### 6.3.2 `returnTo`

`returnTo` 是“来源页 URL”。比如从风险页进入门店详情，链接会变成：

```
/stores/70?returnTo=%2Frisk%3Fdomain%3DR4%26page%3D2
```

详情页读这个参数，返回时跳回去。

但它不能直接信任。用户可以手工改成外链、`javascript:`、路径穿越、超长 URL。

于是有了 `safeReturnTo`。

### 6.3.3 S-01：路径穿越

C-1 审计发现了一个问题：

```
/cities-stores/../risk
```

`new URL` 会把它规范化成 `/risk`，而 `/risk` 在白名单里，所以通过了校验。

虽然没有造成开放重定向（最终还是站内路径），但它违反了“解析前拒绝穿越”的原则。

修正方式前面已经讲过：先看原始路径、重复解码、再走白名单。

C-1 最终 23 个 vitest、8 个 E2E 通过。

## 6.4 C-2：精确组合与门店 SKU

C-2 是“业务下钻”的第一步。

它做了两件事：

1. 风险页支持“精确组合”筛选；
2. 门店详情页增加“该店 SKU”列表，并支持进入商品详情。

### 6.4.1 精确组合筛选

风险页的“风险组合”表有 16 行精确组合。点击某一行，URL 写入：

```
/risk?exact_combo=缺货+高零销
```

后端 `_store_where` 会先确认这个组合在 `v_risk_exact` 全集里，然后追加：

```sql
WHERE exact_combo = ?
```

结果是 38 家。

再次点击同一行，清除 `exact_combo`，恢复 888 家。

### 6.4.2 门店 SKU

门店详情页新增“该店 SKU（观察期内）”区块：

- 端点 `/stores/{id}/skus`；
- 支持“全部/仅风险 SKU”；
- 支持排序（指数、零销天数、缺货天数、SKU 编号）；
- 分页 50；
- 点击 SKU 进入商品详情。

后端用 `COUNT(*) OVER()` 一次查询取总数，避免两次扫描。

### 6.4.3 C-2 审计的四个提示

C-2 审计没有阻断/重要/一般问题，但留了四个提示：

1. 多级返回会丢更上层 context；
2. 商品风险页没有 `returnTo`；
3. 低 SKU 提示重复；
4. 手工 `combo=at_least&exact_combo` 会导致 UI 与筛选不一致。

这四条当时没有修，留给 C-4 处理。

## 6.5 C-3：至少组合

C-3 增加“至少组合”筛选。

### 6.5.1 参数设计

URL 参数是：

```
/risk?domains=stockout_domain,R4&combo=at_least
```

后端 `_store_where` 会：

- 校验 `domains` 与 `risk_domain`/`exact_combo` 互斥；
- 拆分两个码；
- 确认都在 `{stockout_domain,R3,R4,R5,R6}`；
- 追加 `stockout_domain IS TRUE AND R4 IS TRUE`。

结果是 56 家。

### 6.5.2 10 个组合与 P3-D 的一致性

C-3 审计逐一比对了 10 个至少组合与 P3-D `d8b`：

| 组合 | P3-D | API | 一致 |
|---|---:|---:|---|
| 缺货 + 持续低销 | 9 | 9 | 是 |
| 缺货 + 高零销 | 56 | 56 | 是 |
| 缺货 + 高波动 | 31 | 31 | 是 |
| 缺货 + 高异常日 | 24 | 24 | 是 |
| 持续低销 + 高零销 | 3 | 3 | 是 |
| 持续低销 + 高波动 | 44 | 44 | 是 |
| 持续低销 + 高异常日 | 2 | 2 | 是 |
| 高零销 + 高波动 | 21 | 21 | 是 |
| 高零销 + 高异常日 | 12 | 12 | 是 |
| 高波动 + 高异常日 | 18 | 18 | 是 |

10/10 一致。

### 6.5.3 C-3 审计的四个提示

1. 空 `domains=` 等同未传；
2. 只枚举 10 个跨域两两组合；
3. C-2 的四项提示未处理；
4. 选中行没有高亮。

同样留给 C-4。

## 6.6 C-4：整体验收与七项遗留

C-4 不是“再做一个功能”，而是“把前面三个阶段留下的洞补上，并做整体验收”。

C-4 处理的七项遗留是：

| # | 遗留 | 处理 |
|---:|---|---|
| 1 | 多级返回丢状态 | 新增 `BackLink`，优先浏览器历史 |
| 2 | 商品风险页无 `returnTo` | 行点击补 `buildReturnTo` |
| 3 | 低 SKU 提示重复 | 删除 SKU 区块重复提示，只留顶部 |
| 4 | 手工参数冲突 | `effectiveExactCombo`，以 `domains` 为准 + 警告 |
| 5 | 空 `domains` | 后端改为 400 |
| 6 | 高阶至少组合不枚举 | 设计内限制，不处理 |
| 7 | 至少组合选中行无高亮 | `rowClassName` + `active-row` |

### 6.6.1 BackLink：为什么不是简单地改 `returnTo`

第一版的想法是“让 `returnTo` 保留嵌套”。但这样会循环：A 返回 B，B 返回 A。

第二版的想法是“用全局状态保存导航栈”。但这会引入新的状态管理，且刷新后消失。

最终选择浏览器历史：

```tsx
const useHistory = Boolean(returnTo) && location.key !== 'default'
```

- 有站内历史：`nav(-1)`；
- 刷新/直达：`returnTo`；
- 都没有：默认页。

`location.key !== 'default'` 是关键：它区分“站内导航过来的”和“直接打开/刷新的”。直接打开时没有历史可退，只能用 `returnTo`。

### 6.6.2 低 SKU 提示为什么重复

门店详情页原本有两处提示：

- 页面顶部：“该门店 SKU<10，仅保留基础档案……”；
- SKU 区块：“该店 SKU<10……”。

内容几乎一样，用户会以为出现了两个问题。

修正方式是删除区块内重复提示，只保留顶部。E2E 增加了“只出现一次”的断言。

### 6.6.3 冲突参数为什么以 `domains` 为准

手工 URL 同时带 `exact_combo` 和 `domains` 时，有两种处理：

1. 以 `exact_combo` 为准；
2. 以 `domains` 为准。

项目选择 `domains`，理由是：

- `domains` 是 C-3 新增的“至少”语义，范围更宽；
- 如果以精确为准，用户会以为“至少”没生效；
- 显示警告，告诉用户 URL 冲突。

后端仍然保持严格互斥（直接调用 API 会 400）。前端只是“在请求前降级”，不是“放宽后端”。

### 6.6.4 空 `domains` 为什么要 400

C-3 时，空 `domains=` 被当作“没传”，返回 888 家。

但用户看到 URL 里有 `domains=`，会以为在筛选。这是一种“假筛选”。

C-4 把它改成 400，并同步单测。这样用户会明确知道参数不合法，而不是被静默忽略。

### 6.6.5 高阶至少组合为什么不枚举

C-3 只展示 10 个“跨域两两组合”。三域、四域、五域同时命中的组合没有枚举。

原因是：

- P3-D `d8b` 的冻结口径就是 10 对；
- 高阶组合数量增长快，展示会爆炸；
- 精确组合已经覆盖了“完整域集合”的需求。

页面脚注明确写了这一点，避免用户以为“只有这 10 种”。

### 6.6.6 选中行高亮

精确表和至少表都支持 `rowClassName`：

- 精确：`effectiveExactCombo === r.combination`；
- 至少：解析组合字符串，与 `domainPair` 比较。

CSS 增加：

```css
tbody tr.active-row { background: #eff6ff; }
```

这样用户能一眼看出“当前筛选的是哪一行”。

### 6.6.7 全量回归

C-4 最后做了完整回归：

- pytest 101；
- vitest 23；
- E2E 56（C-1 8、C-2 9、C-3 6、C-4 7、BI-1 9、商品 17）；
- build 637 modules；
- 25/25 SHA；
- 21 项边界探针。

结论：建议 BI-2-C 正式通过并 Feature Freeze。

## 6.7 最终产品形态

到 C-4 结束时，BI 的最终形态是：

```
/overview              经营总览
/cities-stores         城市与门店（合并页）
/risk                  经营风险（精确/至少切换）
/stores/:storeId       门店详情（SKU 列表）
/products              商品总览
/products/list         商品列表
/products/risk         商品风险
/products/categories   商品类别
/products/:productId   商品详情
*                      404
```

### 6.7.1 一条完整的用户路径

1. 打开总览，确认 898/888；
2. 进入城市与门店，选 C03；
3. 点击门店 S0070；
4. 在“该店 SKU”里点一个 SKU；
5. 进入商品详情；
6. 点返回，回到门店；
7. 再点返回，回到城市页，C03 还在；
8. 进入风险页，选“缺货+高零销”精确组合（38 家）；
9. 点门店，进入详情；
10. 返回，组合和页码还在；
11. 切换“至少同时命中”（56 家）；
12. 点“取消至少组合”，回到 888。

这条路径在 C-1/C-2/C-3/C-4 的 E2E 里被逐段验证。

### 6.7.2 状态模型

最终的状态模型非常简单：

- 筛选、分页、组合 → URL；
- 来源页 → `returnTo`；
- 多级返回 → 浏览器历史；
- 服务端数据 → `useApi`；
- UI 状态 → 组件内部。

没有 Redux，没有 Zustand，没有 React Query。

这不是“刻意不用”，而是在当前复杂度下，URL + 自研 Hook 已经够了。

## 6.9 这一章的意义

BI-2-C 看起来只是“加几个筛选”，但它实际上是整个项目产品化程度最高的一段。

它把前面所有分析结果，变成了用户可以“顺着问题走”的路径：

- 从城市到门店；
- 从门店到 SKU；
- 从 SKU 到商品；
- 从风险组合到门店；
- 从任意一层返回，状态不丢。

在这个过程中，项目处理了：

- URL 状态；
- 返回语义；
- 多级导航；
- 路径穿越；
- 参数冲突；
- 空值语义；
- 小样本提示；
- 选中高亮。

这些细节不改变任何分析结论，但它们决定了用户能不能真正“用起来”。
