# 第三章 地基之上：P1–P3 如何把“数据”变成“口径系统”

## 3.1 进入这一章时的状态

第二章结束时，项目已经有了一条可复现的流水线：原始 Parquet 经过校验、清洗、聚合，产出 13 张派生表；18 项测试通过；所有数字都能从原始文件重建。

但这时还没有任何“经营结论”。

项目知道的只是：

- 每天卖了多少（销量指数）；
- 每个门店、每个 SKU 大概是什么规模；
- 缺货、折扣、天气等字段是什么样。

不知道的是：

- 整体趋势怎么描述？
- 哪些门店异常？
- 哪些 SKU 值得关注？
- 城市之间怎么比较？
- 门店之间的差异是“规模”造成的，还是“效率”造成的？
- 哪些门店有风险？风险怎么定义？

这些问题，构成了 P1–P3 的工作。

---

## 3.2 P1：先看整体，再看门店

P1 的目标是“销量经营状况”，回答四个问题：

1. 整体销量趋势如何？
2. 有没有异常日？
3. 门店之间差异多大？
4. 哪些门店持续低销？

### 3.2.1 三层口径

P1 一开始就遇到一个看似简单、实际上很容易错的问题：**“日均销量”到底怎么算？**

同一份数据，至少可以有三层口径：

| 口径 | 公式 | 回答的问题 |
|---|---|---|
| 样本总销量指数 | `SUM(sales_index)` | 整个样本每天卖了多少 |
| 单店日均销量指数 | `SUM / 门店-日数` | 平均一家店每天卖多少 |
| 单序列日均销量指数 | `SUM / 序列-日数` | 平均一个“门店×SKU”每天卖多少 |

这三个数字不一样，而且回答的问题不一样。

- 总指数会被门店数量影响；
- 单店日均适合横向比较门店/城市；
- 单序列日均适合比较商品，但会被“覆盖门店数”影响。

P1 把这三层都保留下来，并在报告里分别标注用途。这个决定看起来只是“多写几个指标”，但它避免了后面大量的口径混用。

后来 P2 的“单店日均”分母错配，本质上就是这三层口径没有贯彻到底。

### 3.2.2 异常日：为什么用稳健 z

P1 需要判断“哪些天是异常日”。

最直觉的做法是：算均值、算标准差，超过均值 ± 3 个标准差就算异常。

但销量数据是长尾的，还有促销尖峰。均值和标准差会被异常值拉偏，导致“异常”本身被稀释。

P1 选择了稳健 z：

```
med = 中位数(x)
mad = 中位数(|x - med|)
robust_z = (x - med) / (1.4826 × mad)
|robust_z| > 3 → 异常
```

为什么要乘 1.4826？因为在正态分布下，MAD 与标准差的换算系数约为 1.4826。乘上它，稳健 z 的尺度才和标准 z 接近。

这个方法的优点是：中位数和 MAD 都不容易被少数极端值拉走。

结果是：90 天里只有 1 天被判定为异常（稳健 z = 3.26）。

### 3.2.3 持续低销：不是“某天卖得少”

P1 还需要识别“持续低销”的门店。

“某天卖得少”很常见，不能叫持续低销。P1 的定义是：

```
7 日滚动均值 < 0.7 × 该门店中位
且连续 ≥ 7 天
```

这个定义有两个关键点：

1. **相对自己，而不是相对别人。** 用门店自己的中位数做基准，避免“小店永远低销”的误判。
2. **连续 7 天。** 过滤掉单日波动。

这个规则后来被 P3-D 复用为 R3，但也埋下了一个隐患：P1 只把“≥7 天”的门店写进结果表，未达标门店在后续合并时被填 0。这个问题在 P3-D 才被发现。

### 3.2.4 P1 的其他工作

P1 还做了：

- 星期效应；
- 小时份额、时段汇总；
- 7×24 热力图；
- 门店规模/效率表；
- 门店分布（P10/P25/P75/P90、Top10%/20% 份额、Spearman）；
- 门店四分位画像；
- 三类异常（日级、门店截面、门店-日时序）。

输出是 12 张表、9 张图、一份 `summary.json`。

P1 的结论是描述性的：总指数 4,493,660.787；日总指数范围 34,893–72,939；门店健康度分档（优 6/良 156/中 715/低 21，仅冒烟参考）。

## 3.3 P2：商品经营的第一次“深水区”

P1 看的是“整体与门店”，P2 转向“商品”。

P2 要回答：

- 哪些 SKU 贡献最大？
- 覆盖广度和单店效率是否矛盾？
- 哪些 SKU 有风险？
- 类别结构如何？

### 3.3.1 规模与效率的双榜

P2 发现一个很典型的现象：**卖得最多的 SKU，不一定是单店效率最高的 SKU。**

比如一个 SKU 覆盖 783 家门店，总销量很高，但单店日均可能只有 2.60；另一个 SKU 只覆盖 131 家门店，总销量低，但单店日均 15.56。

如果只按总量排名，会误以为前者“更强”；如果只按单店效率排名，又会忽略覆盖广度。

P2 因此做了双榜：

- 规模榜：按累计指数；
- 效率榜：按单序列日均，并设置“覆盖门店数 ≥5”的门槛（540 个 SKU）。

这个门槛不是统计定理，而是经验规则：覆盖太少的 SKU，单店日均不稳定。

### 3.3.2 Pareto、覆盖敏感性与稳定性

P2 还做了三件事：

1. **Pareto**：Top10% SKU 贡献 72.30%，Top20% 贡献 87.00%，122 个 SKU 贡献 80%。
2. **覆盖敏感性**：把覆盖门槛从 1 调到 100，看排名是否稳定。
3. **稳定性分层**：零销率 × CV 中位，分成四档。

这些工作有一个共同点：它们都在回答“这个排名/结论稳不稳”。

### 3.3.3 四个风险旗标

P2 最终定义四个商品风险旗标：

| 旗标 | 阈值 |
|---|---|
| 高波动 | 序列 CV 中位 > P95（1.060） |
| 高零销 | 零销率 > P95（24.44%） |
| 异常日频繁 | 异常日占比 >5% |
| 门店集中 | 覆盖 ≥5 且 HHI > P95（0.184） |

结果是：117 个 SKU 至少命中一个，35 个命中 ≥2 个，12 个命中 3 个。

## 3.4 第一次审计风暴：P2 的问题不是“代码错”，而是“名字错”

P2 完成后，项目做了一次独立审计。这次审计发现的问题，比“代码跑不通”更值得记录。

### 3.4.1 “单店日均”的分母错了

审计拿明细复算后发现：

- C05 的“单店日均”是 1.184，但按门店-日口径应该是 14.545；
- C22 是 1.795 vs 6.083；
- S029 是 1.319 vs 12.681。

差了大约一个数量级。

原因是：`per_series_day` 的分母是 `COUNT(*)`，也就是 SKU-门店-日，不是门店-日。但字段名和报告都写成“单店日均”。

这导致“C22 单店日均最高”这个结论，在正确口径下不成立。

修正方式不是直接改数字，而是：

- 原指标改名为 `category_sku_store_day_avg`；
- 新增 `category_store_day_avg = 累计指数 / COUNT(DISTINCT store_id, dt)`；
- 新增两张图；
- 报告同步更新。

这个处理方式很值得注意：原指标本身没有错，它只是名字错了。改名 + 新增，比覆盖更安全。

### 3.4.2 四个旗标不是 AND

审计还发现，读者容易把“四个风险旗标”理解成“四个条件同时满足”。

实际上，它们是四条独立标记，按命中数量汇总。一个 SKU 可以只命中高波动，也可以只命中高零销。

这不是代码 bug，而是文档表达问题。修正方式是补充说明：四个旗标相互独立，命中数量只作筛查，不是风险评分。

### 3.4.3 MAD=0 的 75 条序列

审计还发现，有 75 条序列（6,750 行，0.15%）的 MAD 为 0，无法计算稳健 z。

原报告没有披露这一点。修正方式是补充说明：MAD=0 时跳过异常检测，并披露数量。

### 3.4.4 Top10% 是 86 个，不是 87 个

百分比四舍五入与计数不一致，也是一个典型问题。修正后明确写 86 个（9.94%）。

这次审计让项目意识到：**分析报告里最容易错的不是公式，而是“名字、分母、边界、百分比”。**

## 3.5 P3-A：城市比较，先解决“两个缺货率”

P2 之后，项目进入 P3，先做城市对比。

城市分析看起来简单：按城市聚合，比较总量、单店日均、缺货率、集中度。但一开始就遇到一个坑：**缺货率有两个口径。**

| 口径 | 公式 | 含义 |
|---|---|---|
| SKU-日缺货率 | 有缺货的 SKU-日 / 总 SKU-日 | 商品维度：多少商品-天出现过缺货 |
| 小时槽位缺货率 | 缺货小时 / (16 × SKU-日) | 时间维度：所有营业小时里缺货占多少 |

这两个数字不一样，而且不能互相替代。一个门店可能“每天都有 SKU 缺货”（SKU-日率高），但缺货时间很短（小时率低）。

P3-A 把两个口径并列，并在报告里明确区分。

此外，P3-A 还处理了：

- 18 个城市中，门店数 <10 的 5 个城市只展示、不排名；
- 城市相关分析用 1,000 次 bootstrap，`seed=42`；
- City 0（290 家门店）做敏感性对照。

但 P3-A 留下了一个命名隐患：它的 `stockout_sku_day_rate` 是“城市内门店率的简单平均”，而 P3-B/C/D 的同名字段是“门店内比值”。同名不同义，直到 P3-D 才被明确写出来。

## 3.6 P3-B：门店分层，为什么要用 Huber 回归

P3-A 比较的是城市，P3-B 转向门店。

门店之间最大的差异是规模：有的店 SKU 多、销量大，有的店 SKU 少、销量小。直接比“销量”不公平，因为规模不同。

P3-B 要回答的是：**控制规模之后，哪些门店的效率更高或更低？**

### 3.6.1 模型设定

P3-B 用了一个 log-log 模型：

```
x = log(SKU 覆盖数)
y = log(1 + 单 SKU 日均指数)
```

为什么要取对数？

- 销量和 SKU 数都是长尾分布，取对数后更接近线性；
- 斜率可以解释为“SKU 数增加 1%，单 SKU 日均变化约多少”。

然后用稳健回归（RLM）拟合，Huber 的 `M=1.345`。

### 3.6.2 为什么不用普通最小二乘（OLS）

普通最小二乘对异常值很敏感。门店数据里有一些高影响点（比如超大店、超小店），OLS 会被它们拉偏。

Huber 回归的思路是：对残差小的点用平方损失，对残差大的点改用线性损失，降低异常值的影响。

P3-B 同时跑了 OLS、Huber、分位数回归做对照，并输出了：

- 斜率、置信区间；
- hat 值、Cook's D；
- 残差分箱；
- 高影响门店占比；
- 象限一致率。

### 3.6.3 四象限

拟合后，每家门店有一个残差 `eff_resid`，表示“实际效率与模型预期的偏离”。

然后按两个 P50 切四象限：

- 规模轴：`per_day_index` 的 P50；
- 效率轴：`eff_resid` 的 P50。

结果是 261 / 183 / 183 / 261。

10 家 SKU<10 的门店不参与模型，象限填“不参与（SKU<10）”。

### 3.6.4 审计：R² 不是 R²

P3-B 的报告里写了一个 `R²_weighted=0.119...`。

审计指出：它不是标准 R²，而是“基于 RLM 最终权重的样本内加权拟合指数”。而且 0.119 本身说明模型拟合很弱，只能做探索性分层。

此外，≥30 门槛的“一致率 82.23%”只在 681 家交集上成立，207 家没有参与。

修正方式：

- 改名为“加权拟合指数”；
- 结论降级为“弱拟合、仅探索性”；
- 门槛表补“交集/未参与”列。

这个问题的意义不在于数字，而在于：**统计量的名字会直接影响读者对结论强度的判断。**

## 3.7 P3-C：门店商品结构，HHI、熵与聚类

P3-B 看的是“规模与效率”，P3-C 看的是“商品结构”。

同样规模的两家店，可能一家依赖少数头部 SKU，另一家品类很分散。P3-C 要量化这种差异。

### 3.7.1 HHI 与熵

P3-C 用了两个指标：

- **HHI** = Σ(门店内 SKU 份额²)，越大越集中；
- **熵** = -Σ p·ln p，越大越分散。

还算了：

- 有效 SKU = 1/HHI；
- Top1/Top5 份额；
- 类别 HHI、类别熵、一级类别数。

这些指标后来直接进入 BI 的门店详情页和商品结构页。

### 3.7.2 十分位：为什么不用 qcut

P3-C 需要按 SKU 覆盖数把门店分成十组。

最直觉的做法是 `pd.qcut`。但 `qcut` 有一个问题：相同 SKU 数的门店可能被切到不同组，导致“同规模门店不可比”。

P3-C 改用了 `np.array_split`：先按 `sku_count`、`store_id` 排序，再等样本量切分。这样每组 88–89 家，边界确定。

### 3.7.3 聚类

P3-C 还做了门店结构聚类：

- 门店×类别份额矩阵；
- L2 归一化；
- Euclidean 距离；
- Ward 层次聚类；
- `fcluster(k=4)`，输出 G1–G4。

聚类结果后来成为门店详情页的“结构群”，并与四象限交叉，形成 16 个单元格。

### 3.7.4 审计：行序改变了置信区间

P3-C 的审计发现了一个很隐蔽的问题：同一份数据，改变行顺序后，bootstrap 置信区间会变。

原来的 CI 是 −0.798734 ~ −0.734246；按 `store_id` 排序后变成 −0.801941 ~ −0.735777。

原因是：bootstrap 抽样按数组顺序进行，输入行序不同，抽样结果就不同。固定随机种子只能保证“同一行序下可复现”，不能保证“不同行序下可复现”。

修正方式：

- `_spearman_ci` 先按 `store_id` 排序；
- 新增“行序不变性”测试；
- 修正图片路径断链；
- 抽样排除典型店。

测试从 44 增加到 45。

这个问题的教训是：**可复现 = 固定种子 + 固定输入顺序 + 固定实现。**

## 3.8 P3-D：风险标记，R1–R8 的诞生

P3-D 是整个分析阶段最复杂的一块。

它要把“缺货、低销、零销、波动、异常日”统一成风险标记，并回答“哪些门店同时命中多个域”。

### 3.8.1 五个运营域

P3-D 定义了五个运营风险域：

| 域 | 标记 | 阈值 |
|---|---|---|
| 缺货 | R1 或 R2 | 广度/强度 > P90 |
| 持续低销 | R3 | 连续低销 ≥7 天 |
| 高零销 | R4 | 零销率 > P90 |
| 高波动 | R5 | CV > P90 |
| 高异常日 | R6 | 异常日占比 > P90 |

另外还有两个结构提示：

| 提示 | 标记 | 阈值 |
|---|---|---|
| 覆盖偏窄 | R7 | SKU 数 ≤ P10 |
| 结构集中 | R8 | 同 SKU 十分位内 HHI > P90 |

R7/R8 不计入运营域数量。

派生指标：

```
stockout_domain = R1 | R2
domain_count = 五个运营域求和
multi_risk = domain_count >= 2
```

结果是：R1–R8 命中 89/89/90/89/89/56/93/90；多风险 132 家（14.86%）。

### 3.8.2 精确组合与至少组合的起源

P3-D 在处理“门店同时命中多个域”时，发现有两种问法：

- “只命中这两个域的门店有多少？”——这是**精确组合**；
- “至少命中这两个域的门店有多少？”——这是**至少组合**。

这两个问题都合理，但答案不同。

P3-D 把“至少组合”写进了 `d8b` 表：5 个运营域两两组合，共 C(5,2)=10 对。原表有 15 行，其中 5 行是同域对角线（比如“缺货+缺货”），后来 BI 视图用 `WHERE domain_a <> domain_b` 过滤掉，保留 10 对。

“精确组合”则在 P4 才正式成型：只统计 `domain_count >= 2` 的门店，按完整域集合分组，共 16 种。

两者最典型的对比是“缺货+高零销”：

- 精确：38 家；
- 至少：56 家。

38 家是“只命中缺货和高零销”的门店；56 家是“至少命中这两个域”的门店，包含 38 家以及其他域的门店。

这个区分后来成为 BI 风险页的核心交互。

### 3.8.3 审计：整体缺货率被二次加权

P3-D 报告最初写整体缺货率 0.4434 / 0.2027。

审计复算发现：这个数字是“先按城市算率，再按门店数加权”，不是池化率。正确池化值应该是：

- SKU-日：0.442668（1,992,006 / 4,500,000）；
- 小时槽位：0.198771（14,311,536 / 72,000,000）。

为什么“城市率再按门店数加权”不对？因为门店数大的城市被重复加权，等于放大了大连锁的影响。

修正方式是改为池化率：总分子 / 总分母。这个值可以直接在 4.5M 行明细上对账。

### 3.8.4 审计：54 家低销门店消失了

P3-D 还发现一个上游遗留问题：`max_low_run_days` 在 P1 被截断，P3-B 又 `fillna(0)`，导致主样本中 54 家真实连续低销 1–6 天的门店被记成 0。

P3-D 没有修改 P1/P3-B 的历史文件，而是按 P1 规则从 `agg_store_day.parquet` 独立复算，新增 `low_run_max_days` 字段，恢复了 54 家门店的真实天数。

R3 仍使用 P1 的二元定义（≥7 天），但 `low_run_max_days` 让后续分析能看到完整分布。

### 3.8.5 敏感性

P3-D 还做了大量敏感性分析：

- 阈值 P85/P90/P95；
- minSKU 5/20/30；
- 城市内 P90；
- 剔除 City 0。

这些分析不能证明“阈值正确”，但能说明“结论对阈值是否敏感”。

## 3.9 P3 整体验收：指标字典的诞生

P3-A/B/C/D 都完成后，项目做了一次整体验收。

验收发现的问题包括：

- 文字表述不准确（“前 6 组为正”实际是前 9 组正）；
- 图片路径断链；
- 缺少验收签认；
- 缺少跨阶段指标字典。

最后一项最关键。因为 P1–P3 产生了大量指标，同名不同义的情况已经开始出现：

- P3-A 的 `stockout_sku_day_rate` 是城市门店率简单平均；
- P3-B/C/D 的同名字段是门店内比值；
- P3-D 的池化率又对应 P3-A 的 `stockout_day_rate`。

如果不建立指标字典，后面 BI 一定会混用。

于是项目补了 D1–D17 指标字典，明确每个指标的定义、公式、粒度、来源。P3 正式整体验收通过，进入 Feature Freeze。

## 3.10 这一阶段真正建立了什么

从表面看，P1–P3 产出的是一堆 CSV、图和报告。

但从工程角度看，这一阶段真正建立的是三样东西：

### 第一，口径体系

- 三层销量口径；
- 两种缺货口径；
- 门店率/城市率/池化率；
- 精确/至少；
- 运营域/结构提示。

这些口径后来全部进入 BI 的筛选、图表和文案。

### 第二，审计机制

P2、P3-B、P3-C、P3-D 的问题都不是“代码跑不通”，而是“数字/命名/披露不对”。

审计通过“拿明细重算”发现了开发者自己没发现的问题。这个机制后来被沿用到 BI 阶段，成为项目的质量核心。

### 第三，可复现意识

固定 seed、按 store_id 排序、等样本量切分、保留原始值、只标记不修改——这些做法让每个数字都能被复算。

## 3.11 遗留问题如何推动 P4

P1–P3 结束时，项目已经有了完整的分析结果，但这些结果是“分散的”：

- P1 有门店规模/效率；
- P2 有 SKU 风险；
- P3-B 有四象限；
- P3-C 有结构群；
- P3-D 有 R1–R8。

如果直接拿去做 BI，每个页面都要自己拼这些表。更麻烦的是，用户会问：“这家门店到底怎么样？”

要回答这个问题，需要一个“门店级”的整合视图：把规模、效率、结构、风险放在一行里。

这就是 P4 的起点。
