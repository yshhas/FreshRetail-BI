# 第一章 起源：一个想覆盖“从企业到用户”的项目，先被数据拦住了

## 1.1 项目最开始的样子

这个项目最初的名字叫“中国数字零售与本地生活经营增长分析”。

从名字就能看出，它一开始并不想做“一个 BI 网站”。它想做的是一套完整的经营分析：既看企业整体，也看用户价值；既看留存复购，也看商品和区域；最后还能给出诊断与策略。

第一阶段报告把这条链路写得很明确：

```
企业整体经营 → 用户价值 → 留存/复购 → 商品经营 → 区域市场 → 诊断策略
```

站在业务角度，这是一条很自然的分析路径。一个零售企业想知道“经营得怎么样”，通常就会从总盘子开始，往下拆到用户、商品、区域，最后落到“哪里出了问题、该怎么办”。

但这条路径有一个隐含前提，第一阶段的报告也写出来了：**必须有一份订单级交易明细**。订单 ID、金额、时间、用户、商品，五个要素要同时具备。

- 没有订单 ID，就无法把同一笔交易里的商品放在一起看；
- 没有金额，就无法算客单价、GMV、利润；
- 没有用户 ID，就无法做新老客、复购、留存、RFM；
- 没有时间，就无法做趋势、周期、复购间隔；
- 没有商品，就无法做品类、结构、关联。

这五个要素缺一个，整条链路就会断一截。而项目最初并没有意识到，这五要素在公开数据里有多难同时拿到。

---

## 1.2 第一轮找数据：一份一份看，一份一份否

第一阶段的文档不是“先选一个数据集，再解释为什么”，而是真的把当时能找到的候选逐一看过。这个过程在 `01_候选数据集第一阶段核验报告.md` 里留下了很详细的记录。

最早的候选里，有几种典型：

**第一种，是国外的经典零售数据集。** 比如 Olist（巴西电商）、UCI Online Retail II（英国零售）。它们有订单、有金额、有商品，结构上很适合做经营分析。但问题也很直接：不是中国零售场景，城市、门店、商品语义都对不上“中国数字零售与本地生活”这个题目。

**第二种，是中国互联网平台行为数据。** 比如淘宝 UserBehavior、天猫订单报表、饿了么曝光样本、TAOBAO-MM。它们看起来“很中国、很大”，但仔细看字段就会发现：

- 淘宝 UserBehavior 有用户、有商品、有点击，但没有金额、没有订单，只有 9 天；
- 天猫订单报表只有 28,010 行，没有 user_id、没有商品，原链接还失效了；
- 饿了么有 1.28 亿样本，但它是曝光样本，不是订单，`total_amt_30` 是快照，不是交易金额；
- TAOBAO-MM 有 8.79M 用户、99M 样本、139 GB，但只有点击标签，没有金额。

**第三种，是学术/竞赛数据。** 比如 CUMCM 2023 C、天池母婴、MDPI 的零售数据。它们往往有真实的业务背景，但要么只有单店、没有地区，要么许可条款不清，要么只对审计开放、无法获取。

**第四种，是商业数据平台。** 比如 CnOpenData。字段可能很全，但付费、行数不公开、没有样本可验证。对一个要公开作品集的项目来说，这不是可选项。

01 报告最后的结论很冷静，也很残酷：

> 若坚持六大模块不得缩减，方案 A 不足以支撑项目；没有任何一套数据能完整支持六大模块中的任何一个模块。

这句话是项目第一次真正的“撞墙”。不是代码写不出来，而是**问题本身没有被数据支撑**。

---

## 1.3 为什么会这样：公开数据的三重限制

站在今天回看，第一轮的挫败并不意外。公开零售数据几乎必然受到三重限制。

### 第一重：隐私

订单级数据包含用户 ID、购买时间、地点、商品组合。这些信息组合起来，足以识别个人。真实企业即使愿意公开，也必须做脱敏、聚合、抽样。脱敏之后，用户 ID 往往被删除或打散，订单 ID 也可能被去掉。

### 第二重：商业敏感

金额、成本、毛利、库存、促销策略，是企业的核心经营信息。公开完整订单明细，等于把定价和供应链暴露给竞争对手。所以公开数据通常只给“销量”“曝光”“点击”，不给金额和成本。

### 第三重：许可

很多数据集来自论文或竞赛，许可只允许研究使用，不允许公开作品集展示；有些数据集只对审计开放；有些数据集的原链接早已失效。即使字段合适，也未必能合法使用。

这三重限制叠加起来，就形成了一个很现实的结果：**想要“中国 + 真实 + 订单级 + 有金额 + 有用户 + 可公开”，几乎不存在。**

项目在第一阶段实际上是在用排除法确认这件事。每否掉一个候选，都是在缩小“理想项目”的可能性。

## 1.4 第二次分叉：Olist 的诱惑

第二阶段做了一个更深入的选择：既然中国数据这么难找，要不要退一步，用 Olist 做完整闭环？

`02_第二阶段核心数据集调研报告.md` 对 Olist 的评价很高：9 张表、约 10 万订单、2016–2018 年、可以做订单、商品、用户、支付、评价、地域的完整分析。从“分析完整性”看，它几乎是理想选择。

但报告同时写了一句很关键的话：如果坚持中国市场定位，没有找到合适的核心数据源。

这就形成了一个真正的路线分叉：

- **路线 A**：放弃“中国”定位，用 Olist 做完整六模块；
- **路线 B**：坚持“中国”定位，缩减模块；
- **路线 C**：继续找中国数据源。

从最终结果看，项目选了 C，并在第三阶段找到了 FreshRetailNet-50K。但在当时，这并不是一个显然的选择。选 A 意味着项目能做得更“完整”，但题目会变成“巴西电商分析”；选 B 意味着要接受大量功能做不了；选 C 意味着继续投入调研，而且不一定找得到。

文档没有记录当时的具体讨论过程。但从 03 报告的结构可以看出，项目并没有立刻放弃中国定位，而是又做了一轮系统的中国数据源补充调研。这个动作本身就说明：**“中国”是这个项目的核心约束，不是可以轻易放弃的修饰词。**

## 1.5 FreshRetailNet-50K 的出现

第三阶段找到了 FreshRetailNet-50K。

这个数据集的基本情况是：

- 来自 Dingdong-Inc（叮咚买菜），生鲜即时零售/前置仓场景；
- CC BY 4.0 许可，允许公开使用与展示；
- 2024 年数据；
- train 4,500,000 行、eval 350,000 行，19 列；
- 50,000 条“门店 × SKU”序列；
- 898 家门店、18 个城市、865 个 SKU；
- 90 天观察期（2024-03-28 至 2024-06-25）；
- 字段包括销量、小时销量、缺货小时数、折扣、节假日标记、活动标记、天气。

它打动项目的地方，不是“字段多”，而是四个维度同时成立（03 报告的判断）：

1. **真实性**：真实零售企业的真实经营数据，不是模拟、不是爬虫拼接；
2. **年份**：2024 年，足够新；
3. **字段完整度**：能支撑销量、商品、缺货、区域、诊断；
4. **许可清晰**：CC BY 4.0，可以公开作品集展示。

在此之前，几乎每个候选都至少有一个维度不成立。FreshRetailNet 是第一个“四个维度都能过线”的。

但它也有非常明确的代价。

---

## 1.6 接受代价：没有金额、没有用户、只有 90 天

FreshRetailNet 没有订单 ID，没有用户 ID，没有金额。

它的 `sale_amount` 不是销售额，而是“全局归一化后的销售数量”。这句话在第四阶段才被彻底确认，但在第三阶段选择它时，项目其实已经知道自己要放弃什么：

- 不能做 GMV、销售额、客单价、利润；
- 不能做用户数、新老客、RFM、复购、留存、Cohort；
- 不能做订单量、退款率、支付分析；
- 只有 90 天，不能做年度趋势、季节长期变化；
- 城市、门店、商品都是匿名 ID，没有真实名称。

03 报告把这些写成了一份“必须接受”的清单。这份清单很重要，因为它决定了后面所有阶段的边界。

站在产品角度，这是一次很典型的取舍：**用分析范围的收缩，换取数据的真实性和可展示性。**

如果当时选了 Olist，项目可能会有更完整的“经营分析”，但它就不再是“中国数字零售与本地生活”的项目；如果继续等一份“完美中国数据”，项目可能永远无法开始。

## 1.7 第一阶段结束时，项目其实还很模糊

第一至第三阶段结束时，项目已经有了数据方向，但产品形态仍然模糊。

当时能确定的是：

- 数据是真实的、中国的、可公开的；
- 可以做销量、商品、缺货、区域；
- 不能做金额、用户、订单。

不能确定的是：

- 最终交付是报告、图表，还是网站？
- 目标用户是谁？
- 分析模块怎么划分？
- 指标口径怎么统一？
- 数据质量到底如何？

这些问题在第四阶段才真正开始回答。

值得注意的是，目标用户在前期文档里并没有被正式定义。直到 BI 设计方案（09）才出现 6 类角色：经营负责人、城市/区域运营、门店运营、商品/品类运营、数据分析师、数据管理员。

这是一个很真实的项目特征：**先有数据，再倒推需求，最后才补用户角色。** 它不符合“先访谈用户、再找数据”的理想流程，但它符合一个个人项目在真实约束下的推进方式。

## 1.8 本章的技术注脚：什么是“订单级数据”，为什么它重要

这一章反复出现“订单级数据”，值得单独解释一下。

所谓订单级数据，是指每一行代表“一笔订单中的一个商品”，至少包含：

| 要素 | 作用 |
|---|---|
| 订单 ID | 把同一笔交易的多个商品关联起来 |
| 用户 ID | 识别同一个人的多次购买 |
| 商品 ID | 识别买的是什么 |
| 时间 | 识别什么时候买、间隔多久 |
| 金额/数量 | 识别买了多少、花了多少 |
| 门店/渠道 | 识别在哪里买 |

有了这些要素，才能做：

- 客单价 = 订单金额 / 订单数；
- 复购率 = 重复购买用户 / 总用户；
- 留存 = 某段时间后仍然购买的用户比例；
- 关联销售 = 同一订单中经常一起出现的商品；
- RFM = 最近购买、购买频率、购买金额。

FreshRetailNet 的数据粒度是“门店 × SKU × 日”，不是“订单”。它能回答“某店某天某商品卖了多少、缺货多久”，但不能回答“谁买的、和什么一起买的、花了多少钱”。

这就是为什么项目后来所有分析都围绕“销量指数、缺货、结构、风险”，而不是“金额、用户、复购”。

不是项目不想做，而是数据粒度决定了能做与不能做。

## 1.9 本章的留下的问题

第一阶段结束时，项目留下三个必须解决的问题：

1. **数据到底可不可信？** 下载的文件是否与官方一致？字段类型、行数、主键、日期是否可靠？
2. **`sale_amount` 到底是什么？** 如果它是金额，项目还有救；如果它不是，整个叙事要改。
3. **需求到底砍到什么程度？** 六模块里哪些能保留，哪些必须删除？

这三个问题，推动了第二阶段的全部工作。
