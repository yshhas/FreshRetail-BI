# 第二章 前期：先证明数据可信，再决定项目还能做什么

## 2.1 进入这一章时的状态

第一章结束时，项目已经选定 FreshRetailNet-50K，但还停留在一份“看起来合适”的数据集上。

当时没有回答的问题至少有三个：

- 下载下来的文件，和官方发布的是同一份吗？
- 19 个字段的类型、行数、主键、日期范围，和说明一致吗？
- `sale_amount` 到底是不是金额？

这三个问题不解决，后面任何分析都没有意义。于是项目进入第四阶段：数据获取与质量核验。

---

## 2.2 为什么第一步是哈希校验

第四阶段做的第一件事，不是读数据，而是校验文件。

具体做法是：拿官方 Hugging Face LFS manifest 里记录的文件大小和 SHA-256，和本地下载的文件逐一比对。

SHA-256 是一种哈希算法。你可以把它理解成给文件算一个“指纹”：文件内容只要改动一个字节，指纹就会完全不同。它的用途不是加密，而是**证明你拿到的文件和发布者说的那份完全一致**。

这一步在数据项目里非常关键，原因有三个：

1. **镜像站可能不一致。** 项目当时的网络无法直接访问 huggingface.co，改用了 hf-mirror。镜像本身可能同步延迟、截断或损坏。
2. **下载可能中断。** 100MB 的 Parquet 文件如果下载不完整，pandas 有时仍然能读出一部分数据，报错却出现在很后面。
3. **后续所有结论都依赖这份文件。** 如果文件本身不是官方版本，后面的清洗、指标、报告全部作废。

校验结果：

| 文件 | 大小 | SHA-256 |
|---|---:|---|
| `train.parquet` | 106,436,287 B | `6706832d…de5a3d` |
| `eval.parquet` | 8,440,124 B | `1b118840…995e960e` |

两者都与官方 LFS 记录一致。

这一步看起来“没有产出”，但它给整个项目提供了一个可以反复引用的前提：**后面的所有数字，都是在这两个文件上算出来的。**

## 2.3 质量核验：数据比想象中干净，也比想象中复杂

文件校验通过后，项目开始检查数据本身。

### 2.3.1 结构：4.5M 行、19 列、零重复、零空值

train 的结构是：

- 4,500,000 行 × 19 列；
- 50,000 条“门店 × SKU”序列，完全平衡（每条序列 90 天）；
- 898 家门店、18 个城市、865 个 SKU；
- 类目层级 32 / 84 / 233；
- 主键 `(dt, store_id, product_id)` 零重复；
- 19 个字段空值全为 0；
- 重复行 0、负值 0、全零序列 0；
- `hours_sale` 合计与 `sale_amount` 的最大误差是 1.4e-14。

1.4e-14 是什么概念？这是浮点数计算误差的量级，基本可以认为两者完全相等。这个检查很重要，因为它证明小时字段不是随便填的，而是与日销量严格自洽。

### 2.3.2 三个异常：discount=0、discount>1、销量为零

数据整体很干净，但不是没有异常。

**第一个异常：`discount=0` 有 16,039 行（0.36%）。**

官方定义是 `discount=1.0` 表示无折扣。那么 `discount=0` 是什么？如果是“0 折”，那就是极端促销；但它更像是一个缺失编码。文档没有说明。

项目没有删除这些行，也没有填补，而是新增了一个 `discount_missing` 标记。这个选择在后来的清洗规则里变成了 R002。

**第二个异常：`discount>1` 有 34 行，最大 1.088。**

折扣大于 1 在业务上不合理，可能是数据录入或计算问题。项目同样没有改原值，而是标记 `discount_out_of_range`，促销分析时排除。

**第三个异常：`sale_amount=0` 有 200,760 行（4.46%）。**

零销量不一定是“没人买”，也可能是“缺货”。数据显示，这 200,760 行里有 76.62% 伴随缺货。这个发现直接影响后面所有分析：**零销率不能被解释为“需求为零”。**

### 2.3.3 长尾：均值 0.999，中位数 0.7，最大 44.9

`sale_amount` 的分布不是正态的：

- 中位数 0.7；
- 均值 0.999；
- 最大值 44.9；
- 偏度 8.47。

这意味着少数商品/门店的销量远高于大多数。后续所有“平均”“排名”“异常检测”都必须考虑长尾，不能直接用均值和标准差。

## 2.4 口径危机：`sale_amount` 不是金额

这是整个项目最重要的一个发现。

在第三阶段，项目曾把 `sale_amount` 理解为“销售额”，甚至推测单位可能是“万元”。这个推测很自然：字段名里有 `amount`，零售分析又通常以金额为核心。

但第四阶段核对官方说明后发现：`sale_amount` 是“全局归一化后的销售数量（再乘特定系数）”，**不是金额，不是件数**。

这个发现带来的冲击是连锁的：

1. 所有“销售额、GMV、客单价、利润”类分析全部失效；
2. 之前基于“金额”写的叙事需要全部改写；
3. 项目定位必须从“金额经营分析”改成“销量经营分析”；
4. 后面所有文案都必须避免“销售额”三个字。

第四阶段报告用了一个很明确的表述：第三阶段“可能为万元”的推测作废。

从工程角度看，这是一次“地基级”的纠错。如果这个错误没有被发现，后面会发生什么？

- P1 会把“日销售总额”写成“日销售额”；
- P2 会把“SKU 贡献金额”写成“SKU 销售额”；
- P3 会把“城市销售额对比”写成经营结论；
- BI 页面会出现“GMV”“客单价”等根本不存在的指标；
- 所有数字看起来都很合理，但全部建立在一个错误单位上。

这类错误最危险的地方在于：**它不会让程序报错。** 数据能算、图能画、页面能显示，只是解释错了。

项目在这里停下来纠正，而不是继续往前走，是后面所有工作能成立的前提。

## 2.5 需求大裁剪：从六模块到四块

口径确认后，项目必须回答一个产品问题：既然没有金额、没有用户、没有订单，原来设想的六模块还能留下多少？

第五阶段报告给出了非常清晰的处置清单。

### 保留并重定义

| 原模块 | 调整后 |
|---|---|
| 模块一 企业整体经营 | 销量经营状况 |
| 模块四 商品经营 | 商品销量与缺货经营 |
| 模块五 区域市场 | 区域销量对比 |
| 模块六 诊断策略 | 运营诊断与策略 |

### 删除

GMV、销售额、客单价、订单量、退款率、支付/利润分析、用户数、新老客、RFM、复购率、留存率、Cohort、流失预测、区域客单价、配送时效。

### 降级

模块二（用户价值）、模块三（留存复购）不再产出指标，只保留“为什么不能做”的说明。

这次裁剪的意义，不只是“少做几个功能”。它确立了项目的一条基本原则：

> 每个保留下来的指标，都必须能追溯到字段、公式和样本。

不能追溯的，宁可删掉，也不要用叙事补上。

从产品角度看，这是一次“减法”。从工程角度看，这是把项目从“无法验证的宏大叙事”拉回到“可以逐项验收的分析系统”。

## 2.6 技术底座的第一次成型：为什么是 DuckDB + Parquet

需求裁剪完成后，项目面临第一个真正的技术选择：数据怎么存、怎么算。

当时的约束是：

- 4,500,000 行 × 19 列；
- 小时字段是数组，展开后是 1.08 亿行；
- 需要反复做分组、聚合、分位、窗口计算；
- 运行环境是单机 Windows；
- 没有数据库运维预算；
- 后续 BI 还要读这些结果。

### 2.6.1 先解释 Parquet

Parquet 是一种列式存储格式。

传统 CSV 是“按行”存的：一行一行的字段连在一起。列式存储是“按列”存的：同一列的值放在一起。

为什么分析型场景喜欢列式？

- 分析通常只读少数几列（比如只算 `store_id`、`dt`、`sale_amount`），列式可以跳过不需要的列；
- 同一列的数据类型一致，压缩率高；
- 可以按列做向量化计算，速度快。

代价是：逐行写入、频繁更新不如行式数据库方便。但这个项目是“一次写入、多次分析”，正好适合列式。

### 2.6.2 再解释 DuckDB

DuckDB 是一个“嵌入式分析型数据库”。

“嵌入式”意味着它不像 PostgreSQL/MySQL 那样需要单独启动一个服务进程；它直接跑在 Python 进程里，像 SQLite 一样开箱即用。

“分析型”意味着它擅长的是大范围扫描、分组聚合、窗口函数，而不是高并发事务。

它可以直接查询 Parquet 文件：

```sql
CREATE VIEW raw_train AS
SELECT * FROM read_parquet('data/raw/freshretailnet50k/train.parquet');
```

这条语句没有复制数据，只是建立了一个视图。后面的 SQL 可以直接在这份 Parquet 上执行。

### 2.6.3 为什么不用 PostgreSQL/MySQL

如果用一个传统关系数据库，需要：

- 安装数据库服务；
- 建库、建表、定义 schema；
- 把 4.5M 行导进去；
- 管理用户、权限、备份；
- 维护版本与连接池。

这些工作不是做不到，而是对这个项目“不划算”：数据是只读的、分析是单机的、没有并发写入。引入数据库服务只会增加部署与维护成本。

DuckDB 的优势正好对应这些约束：

- 不需要服务；
- 直接读 Parquet；
- SQL 支持窗口函数、`unnest`、`generate_subscripts`；
- 结果可以再写成 Parquet，供 pandas 和 BI 读取。

### 2.6.4 代价

这个选择也有代价：

- 单机、单进程，并发能力弱；
- 不支持高并发写入；
- SQL 方言与 PostgreSQL 有差异；
- CSV 视图没有传统索引，性能优化只能靠 SQL 写法。

项目后来在 BI 层遇到“单连接串行”的扩展性问题，就是从这个选择延续下来的。但在当前数据规模下，它是合理的。

## 2.7 清洗规则：只加列，不删行

技术底座确定后，项目开始设计清洗。

清洗最容易犯的错误，是“为了让数据好看而修改数据”：删掉异常行、填补空值、修正折扣。这样做的后果是，原始证据消失了，后面无法解释“为什么这个数字和原始数据对不上”。

项目选择了一条更克制的方式：**只新增派生列，不覆盖任何原始列；不删行、不去重、不填补。**

最终形成了 12 条规则（R001–R012）：

| 规则 | 字段 | 条件 | 动作 |
|---|---|---|---|
| R001 | `sale_amount` | 总是 | 新增 `sales_index`，仅复制 |
| R002 | `discount` | `=0` | `discount_missing=TRUE` |
| R003 | `discount` | `>1` | `discount_out_of_range=TRUE` |
| R004 | `discount` | `0<d<=1` | `discount_valid=TRUE` |
| R005 | `discount` | `0<d<1` | `promo_flag=TRUE` |
| R006 | `holiday_flag` | 总是 | `holiday_proxy` |
| R007 | `stock_hour6_22_cnt` | 总是 | `stockout_hours_6_22` |
| R008 | `stock_hour6_22_cnt` | `>0` | `stockout_day_flag=TRUE` |
| R009 | `stock_hour6_22_cnt` | 总是 | `stockout_rate_6_22 = cnt/16` |
| R010 | `sale_amount` | `=0` | `sales_zero_flag=TRUE` |
| R011 | `activity_flag` | 总是 | 保留原值 |
| R012 | 天气四字段 | 总是 | 保留原值，不换算 |

其中 R009 的分母 16 不是随便写的。官方说缺货窗口是 6:00–22:00，但数据实测 `stock_hour6_22_cnt` 恰好等于 `hours_stock_status[6:22]` 的和，也就是索引 6 到 21，共 16 个小时槽位。

这个细节后来被写进 `config.py` 的 `STOCK_WINDOW_HOURS = 16`，并在测试里锁定。它看起来只是一个小常量，但它决定了后面所有缺货率的分母。

## 2.8 基础设施落地：第一次跑通

第六阶段把上述设计写成了代码：

```
src/freshretail/
  config.py          路径、契约、口径常量
  contracts.py       文件/数据帧/切分校验
  cleaning.py        R001–R012
  io.py              SHA-256、JSON、路径转义
  db.py              DuckDB 连接/视图/COPY
  metrics.py         12 个聚合指标
  pipeline.py        流水线编排
  logging_utils.py   JSONL 运行日志
```

流水线的顺序是：

1. 文件校验（大小 + SHA-256）；
2. 元数据契约（行/列/字段顺序/Arrow 类型）；
3. 原始质量检查（主键/空值/负值/日期范围/连续性）；
4. 写 `clean_train.parquet` / `clean_eval.parquet`；
5. 计算 13 张派生表；
6. 写规则、指标、质量报告与运行日志。

第一次完整运行耗时 15.94 秒，跳过哈希复跑 15.38 秒。

结果：

- `clean_train` 4,500,000 行、51.97 MB；
- `clean_eval` 350,000 行、4.43 MB；
- `discount_missing` 16,039；
- `discount_out_of_range` 34；
- `promo_flag` 2,302,806；
- `stockout_day_flag` 1,992,006；
- `sales_zero_flag` 200,760。

18 项测试全部通过（1.59 秒）。

## 2.9 这次“跑通”意味着什么

从表面看，第六阶段只是“把数据清洗了一遍”。但从项目历程看，它完成了三件更基础的事：

### 第一，建立了“可复现”的概念

任何派生文件都可以由 `scripts/build_derived.py` 从原始文件一键重建。运行日志记录了每次运行的输入、输出、行数和耗时。

这意味着：后面任何一个人看到报告里的数字，都可以回到原始文件，重新跑一遍，得到同样的结果。

### 第二，建立了“契约”的概念

`contracts.py` 不只是检查数据，它实际上定义了一份“数据承诺”：

- 文件必须有多少行、多少列；
- 字段必须按什么顺序；
- 类型必须是什么；
- 主键必须唯一；
- 日期必须连续；
- train/eval 必须不重叠。

只要有一项不满足，流水线就中止。这为后面的“冻结”埋下了伏笔。

### 第三，暴露了“不能解释”的边界

第六阶段结束时，文档列了 10 个尚未解决的问题：

1. 归一化系数未知；
2. 城市/门店/商品无字典；
3. `holiday_flag` 语义未确认；
4. `activity_flag` 语义未确认；
5. 天气单位未标注；
6. `discount=0` 视为缺失是推断；
7. 凌晨缺货等于闭店，24 小时缺货率不可用；
8. `store_day_any_stockout_rate` 接近 100%，指标退化；
9. 无代码版本管理；
10. 未做预测基线。

这份清单很重要。它说明项目并没有把“数据跑通”当成“数据没问题”，而是明确知道自己还有哪些不知道。

## 2.10 遗留问题如何影响下一阶段

第六阶段留下了两个直接影响后续工作的隐患。

### 隐患一：`max_low_run_days` 的截断

P1 在做“持续低销”时，只把连续低销 ≥7 天的门店写进 `t11`。P3-B 合并时对未达标门店填 0。

这意味着：一家真实连续低销 1–6 天的门店，在后续表里会显示为 0。

这个隐患在 P3-D 才被审计发现，最终导致 P3-D 必须独立复算真实天数，恢复了 54 家门店的信息。

### 隐患二：没有 Git

第六阶段报告第 17 节明确写着：“无代码版本管理，建议下一阶段初始化 git。”

但项目最终没有产生任何 commit。这直接导致今天写这部纪实时，无法用提交记录还原研发过程，只能靠文档与产物顺序。

这不是一个技术错误，而是一个工程习惯的缺失。它不影响项目能不能跑，但影响项目能不能被追溯。
