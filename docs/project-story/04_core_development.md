# 第四章 从诊断到产品：P4、冻结与 BI 的诞生

## 4.1 进入这一章时的状态

第三章结束时，P1–P3 已经全部验收：销量、商品、城市、门店分层、商品结构、风险标记都有了结果，P3 进入 Feature Freeze。

但项目仍然停留在“分析报告”的形态。

分析结果是分散的：

- P1 有日趋势、门店规模/效率；
- P2 有 SKU 排名、风险旗标；
- P3-B 有四象限；
- P3-C 有结构群；
- P3-D 有 R1–R8、风险组合。

如果用户想知道“这家门店到底怎么样”，需要同时翻 5 份报告。这显然不是产品形态。

于是项目进入 P4：把这些结果整合成“门店档案 + 诊断 + 联动”，为后面的 BI 做准备。

---

## 4.2 P4-A：把门店变成一行

P4-A 的目标很明确：**一行一店，42 个字段，898 行。**

这 42 个字段覆盖：

- 规模：总指数、单店日均、SKU 数；
- 波动：CV、零销率；
- 缺货：SKU-日缺货率、小时槽位缺货率；
- 效率：RLM 残差、权重、高影响标记；
- 结构：SKU HHI、Top1/Top5、类别 HHI/熵、类别数；
- 分组：四象限、结构群；
- 风险：R1–R8、运营域、域数量、多风险；
- 数据质量：`profile_status`（完整档案/基础档案）。

这里有一个很重要的设计决定：**不包含 P1 的 `rank`。**

原因很简单：一旦门店档案里出现“排名”，它就会被当成“经营好坏”的评价，甚至被用于考核。项目从一开始就明确“不做门店排名/评分”。

最终：

- 888 家完整档案（SKU≥10）；
- 10 家基础档案（SKU<10），R1–R8 为 NA，不诊断；
- 42 列，全部来自已验收结果。

---

## 4.3 P4-B：诊断规则与“精确 vs 至少”

P4-B 要回答：“这家门店命中了什么风险？”

它做了三件事。

### 4.3.1 运营域分布

888 家门店的运营域数量分布：

| 域数 | 门店数 |
|---:|---:|
| 0 | 581 |
| 1 | 175 |
| 2 | 101 |
| 3 | 25 |
| 4 | 4 |
| 5 | 2 |

多风险（≥2 域）132 家，占 14.86%；≥3 域 31 家，占 3.49%。

这些数字后来直接进入 BI 的风险页。

### 4.3.2 精确组合

P4-B 只统计 `domain_count >= 2` 的门店，按完整域集合分组：

- 16 种精确组合；
- “缺货+高零销”38 家，排第一；
- “持续低销+高波动”36 家，排第二；
- 其余组合从 10 家到 1 家不等。

精确组合的语义是“恰好只命中这些域”。一家门店只能属于一个精确组合，所以各行可以相加（合计 132）。

### 4.3.3 至少组合

P4-B 还输出“至少同时命中”的门店-域对：

- “缺货+高零销”56 家；
- “持续低销+高波动”44 家；
- “缺货+高波动”31 家；
- “缺货+高异常日”24 家；
- “高零销+高波动”21 家。

“至少”允许其他域同时存在。一家门店可以出现在多个组合里，所以各行不能相加。

精确 38 和至少 56 的关系是：**38 家是 56 家中“只命中这两个域”的那部分。**

这个区分在 P4 报告里被明确写出来，并在后来的 BI 里变成两个可切换的模式。

### 4.3.4 规则库

P4-B 还建立了 11 条规则：

- B0：适用性（进入诊断）；
- B0X：不适用（SKU<10，仅基础档案）；
- B1：无运营域；
- B2-STOCK/LOW/ZERO/VOL/ANOM：五个单域；
- B3：多域；
- S7/S8：结构提示。

规则层次是互斥的：0 域、1 域、≥2 域三者不会同时命中。R7/R8 可独立出现，但不进入运营域。

这个规则库的意义是：让“诊断”变成可解释的规则，而不是一个黑箱评分。

## 4.4 P4-C：把门店和商品连起来

P4-C 是 P4 里最“数据工程”的一块。

它需要建立“门店 × SKU”的关联：

- 哪些 SKU 在某家门店出现过？
- 某家门店有多少风险 SKU？
- 哪些 SKU 经常在同店一起出现？
- 四象限×结构群的 16 个单元格里，风险 SKU 占比是多少？

最终产出：

| 输出 | 内容 | 行数 |
|---|---|---:|
| `p4_c_store_sku_incidence` | 门店×SKU 是否出现 | 50,000 |
| `p4_c_store_sku_risk_summary` | 门店风险 SKU 汇总 | 898 |
| `p4_c_flagged_sku_distribution` | 风险 SKU 覆盖分布 | 117 |
| `p4_c_category_risk_profile` | 类别风险画像 | 32 |
| `p4_c_sku_pair_cooccurrence` | 同店共同出现 | 1,237 |
| `p4_c_quadrant_cluster_cross` | 四象限×结构群 | 16 |

这里有一个后来影响 BI 很大的概念：**“同店共同出现”不是“同时销售”。**

两个 SKU 在同一家门店的 90 天里都出现过，不代表它们同一天都卖出，也不代表消费者一起购买。P4 的文案后来专门改成“观察期内同店共同出现”，并明确不代表同日销售、同日缺货、购买搭配或因果关系。

## 4.5 P4 审计：三个“看起来很小”的问题

P4 完成后，审计发现了三个问题。它们看起来都不大，但都影响用户理解。

### 4.5.1 n<20 的单元格还在展示中位数

P4-C 的四象限×结构群交叉表有 16 个单元格。其中：

- Q1-G2：11 家；
- Q2-G2：17 家；
- Q3-G4：9 家；
- Q4-G1：7 家。

这些单元格的样本量小于 20，但表格仍然展示了中位数。

这违反了项目自己定的“n<20 不比较”规则。

修正方式是：展示层显示 `—`，并标注“样本不足”。后端仍保留原始值用于追溯。

### 4.5.2 “同时销售”容易被误读

P4-C 的共现分析用了“同时销售”这个词。读者很容易理解成“同一天都卖出”或“消费者一起购买”。

但数据里没有订单，也没有购物篮，无法证明这两件事。

修正方式是：统一改成“观察期内同店共同出现”，并在定义里明确它不代表什么。

### 4.5.3 11 条规则没有优先级

P4-B 的规则库有 B0、B0X、B1、B2、B3、S7、S8。文档最初没有说明它们的执行层次，读者可能以为可以同时命中。

修正方式是：补充规则层次说明——B0/B0X 先判断适用性；B1/B2/B3 按域数量互斥；S7/S8 独立。

整改后，P4 测试从 54 增加到 62，正式验收通过并 Feature Freeze。

## 4.6 冻结：为什么要把结果“锁起来”

P4 验收后，项目做了一个很关键的决定：**冻结 P1–P4 的结果。**

具体做法是：

1. 选出 22 个核心结果文件（CSV/Parquet）；
2. 计算每个文件的 SHA-256 和字节数；
3. 写入 `bi/data/freeze_manifest.json`；
4. BI 启动时先校验这 22 个文件；
5. 任何文件被改动，BI 拒绝启动。

后来 BI-2 需要商品资产，契约从 22 项扩到 25 项（增加 3 个文件），版本仍为 `bi0-contract-v2`。

### 4.6.1 为什么需要冻结

如果没有冻结，会发生什么？

- BI 页面读的是某一版 CSV；
- 有人重新跑了一次分析，CSV 被覆盖；
- 页面数字变了，但没人知道为什么；
- 报告里的结论还是旧的，页面和报告对不上。

冻结的作用，是把“分析结果”变成“不可变的事实”。BI 展示的不是“当前算出来的值”，而是“已验收的那一版值”。

### 4.6.2 SHA-256 在这里的作用

SHA-256 在第二章已经用过一次，是为了校验原始文件。这里再用一次，是为了校验分析结果。

区别是：

- 原始文件校验：证明“输入没变”；
- 冻结清单校验：证明“输出没变”。

两者合起来，形成了一条完整的证据链：

```
原始文件（SHA）
  → 清洗/聚合（可重建）
  → 分析结果（SHA）
  → BI 展示
```

任何一个环节被改动，都能被发现。

### 4.6.3 代价

冻结也有代价：

- 新指标必须回到分析层重新计算，不能在前端临时加；
- 数据重跑后必须同步 manifest；
- 测试里硬编码的数字如果与冻结值不一致，会大面积失败。

但对一个“分析结果需要被可信展示”的项目来说，这个代价是值得的。

## 4.7 BI 设计：从“报告”到“产品”

冻结完成后，项目开始设计 BI。

设计方案（09）先检查了现有资产：

- 分析代码：P1–P4 七个模块；
- 派生数据：`data/derived`；
- 分析结果：`data/analysis/p1–p4`；
- 图表：`reports/figures`；
- 测试：62 passed；
- Web/API/容器：**当前不存在**。

然后明确了 BI 的定位：

> 用已验收的 P1–P4 指标，回答“哪里、哪类门店、哪类商品、哪类风险值得复核”，不提供经营评分、门店排名或因果结论。

这不是一句口号，它直接决定了后面所有设计：

- 不做写接口；
- 不做用户系统；
- 不做实时数据；
- 不做 AI/预测；
- 不重算 P1–P4；
- 不做门店排名/评分。

### 4.7.1 页面规划

设计方案规划了 9 个页面：

```
/overview      经营总览
/cities        城市对比
/stores        门店列表
/stores/:id    门店详情
/products      商品 BI
/products/:id  SKU 详情
/risk          经营风险
/explore       联动探查
/methodology   方法与口径
```

实际交付时，页面结构发生了变化：

- `/cities` 和 `/stores` 合并成 `/cities-stores`；
- 商品拆成 5 个页面（总览、列表、风险、类别、详情）；
- `/explore` 和 `/methodology` 没有建。

最终是 9 个业务路由 + 1 个 404 兜底。

### 4.7.2 技术栈

设计选择：

- 前端：React 18 + TypeScript + Vite + ECharts；
- 后端：FastAPI + Pydantic v2；
- 数据：DuckDB + Parquet；
- 部署：Docker Compose（规划，未实施）。

前端状态的设计，文档原本建议 React Query + Zustand。实际实现没有引入这两个库，而是用了自研 `useApi` + URL search params。

这是一个“规划与交付不一致”的地方。它不一定是错误，但它说明：设计文档不是代码，实施时会根据实际复杂度调整。

### 4.7.3 非功能要求

设计方案定了几个硬指标：

- API P95 <500ms；
- `page_size ≤200`；
- 首屏 <2s；
- 只读、无任意 SQL；
- 参数白名单；
- 小样本抑制。

这些指标后来基本达到，但包体积超出了 500kB 警告线。

## 4.8 BI-0：把冻结数据变成 API

BI-0 是 BI 的第一层：只读 API。

它做了四件事：

### 4.8.1 建立 DuckDB 只读视图

第一版建了 22 个视图：

- `v_daily`、`v_hour`、`v_hour_weekday`；
- `v_store_profile`、`v_store_diagnosis`、`v_store_not_applicable`；
- `v_store`（三表合并）；
- `v_city`、`v_store_groups`；
- `v_risk_domain`、`v_risk_exact`、`v_risk_at_least`、`v_risk_quadrant`、`v_risk_cluster`、`v_overall`；
- `v_sku`、`v_sku_risk`、`v_category`；
- 等等。

后来 BI-2-A 增加了 3 个商品视图，总数变成 25。

### 4.8.2 只读安全

BI-0 在 DuckDB 层做了几件事：

```sql
SET autoinstall_known_extensions=false
SET autoload_known_extensions=false
SET allowed_directories=['<data_root>']
SET enable_external_access=false
SET lock_configuration=true
```

这意味着：

- 不能自动安装/加载扩展；
- 只能读 `data/` 目录；
- 不能访问网络/外部文件；
- 配置锁定后不能再改。

此外，`query_df` 还有 SQL 守卫：

- 只允许 `SELECT/WITH`；
- 禁止多语句；
- 禁止 insert/update/drop/copy/read_csv/read_parquet/glob/httpfs 等。

这两层防护（应用层白名单 + 引擎层禁网）是 BI 安全的核心。

### 4.8.3 API 响应契约

所有响应统一为：

```json
{
  "data": [...],
  "meta": {
    "n": 888,
    "sample_scope": "risk",
    "period": "2024-03-28/2024-06-25",
    "data_version": "p1-p4-freeze-2026-11-08",
    "suppressed": false
  },
  "warnings": []
}
```

这个契约让前端只需要一套解析逻辑，也让“样本量、口径、版本、是否抑制”随数据一起返回。

### 4.8.4 冻结校验

BI-0 启动时先跑 `freeze.verify_manifest()`，校验 22 个文件。后来扩到 25 个。

如果校验失败，API 拒绝启动。

这不是“启动检查”那么简单，它是在告诉用户：**你看到的每个数字，都来自一份经过校验的冻结结果。**

## 4.9 BI-1：第一批页面与“标注型整改”

BI-1 做了 4 个页面：

- 经营总览；
- 城市与门店；
- 经营风险；
- 门店详情。

页面本身不难，难的是“怎么让用户不误解”。

### 4.9.1 审计发现的 6 个重要问题

BI-1 审计列出了 6 个重要问题，几乎全部是“作用域标注不清”：

1. 城市页四个区块没有标注“受不受筛选影响”；
2. 选城市后，页面存在“全页已切换”的误读空间；
3. 城市表 101 与门店列表 92 并置，没有说明差异（C03 有 9 家 SKU<10）；
4. 风险组合缺“全样本”标签；
5. 域卡片同时承担“全样本计数”和“筛选入口”，没有标作用域；
6. `at_least` 10 与 `d8b` 15 没有披露。

这些问题不是功能 bug，而是“数字没说清楚它属于谁”。

### 4.9.2 M1–M5：全部用文案解决

整改没有改数据、没有改布局，只加了标注：

- 城市表副标题“全样本 18 城横向参照”；
- 列头“门店数（全部 898）”；
- 散点/同类组/列表分别标注筛选范围；
- 动态“当前筛选 X 家”；
- 组合副标题 + 口径脚注；
- 域卡片“全样本 888 · 点击仅筛选下方门店”。

这就是“标注型整改”：不改计算，只改表达。

### 4.9.3 一次审计误判

BI-1 审计还提了一条“筛选不重置页码”（B-05）。

复核发现这是误判：`useUrlFilters` 早已实现“任何非 page 参数变化就删除 page”，并且有测试。

项目没有因为“审计说了”就改代码，而是用代码复核证明它已经正确，并补了 E2E 固化。

这件事说明：审计也会错，必须用代码和测试复核。

### 4.9.4 验收与冻结

M1–M5 完成后，E2E 9/9，BI-1 正式验收通过并 Feature Freeze（22/22 SHA）。

## 4.10 契约 v2：为商品 BI 扩 3 个文件

BI-1 验收后，项目准备做商品 BI。但商品 BI 需要 3 个 P4/P2/P3-C 的结果文件：

- `p4_c_store_sku_incidence.csv`（50,000 行）；
- `t8_head_tail.csv`（2 行）；
- `c3_category_penetration.csv`（32 行）。

这些文件已经存在并通过验收，但不在原来的 22 项冻结清单里。

于是项目做了契约增量修订：

- 新增 3 项，总数 25；
- 原有 22 项路径与 SHA 不变；
- `data_version` 不变；
- `contract_version` 升为 `bi0-contract-v2`；
- 修订声明 `files_added=3, files_modified=0`。

验收时，项目用内存伪造逐一触发了 9 个失败分支：

- 重复键；
- 绝对路径；
- `..` 穿越；
- SHA 格式错误；
- 文件篡改；
- 文件缺失；
- 字节数不符；
- 增量计数不符；
- 等。

这保证了 manifest 不只是一个“文件列表”，而是一个真正会拒绝异常的契约。

## 4.11 BI-2 前期：先确认“能做什么、不能做什么”

在写商品页面之前，项目先做了 BI-2 前期方案。

它确认了数据可行性：

- 865 个 SKU；
- 117 个风险 SKU；
- 35 个多风险 SKU；
- 1,237 对同店共同出现；
- 32 个一级类别。

同时明确列出了一批“不做”：

- 销售额、价格带、毛利；
- 库存、补货、订单、客流；
- 复购、留存；
- 同日关联销售；
- SKU 日趋势；
- 865×865 全量共现；
- 综合评分；
- 因果结论。

这份“不可做清单”和“可做清单”同样重要。它防止了商品 BI 在开发过程中不断被加需求。

前期还发现了一个口径问题：`high_zero` 在早期报告里写 65，但冻结旗标口径是 43。65 是 `zero_rate>20%` 的描述性口径，43 是 P95 旗标口径。

修正方式：明确两个口径，页面使用 43，并在风险页加提示说明 65 的来源。

## 4.13 BI-2-B：五个商品页面与 B-01

BI-2-B 做了五个页面：

- 商品总览；
- 商品列表；
- 商品风险；
- 商品类别；
- 商品详情。

### 4.13.1 B-01：92/117 个详情页是空白

审计发现一个很严重的产品问题：

商品详情页只展示 `stores_both >= 20` 的共现对，并取前 20。结果在冻结数据中，92/117（78.6%）的风险 SKU 详情页显示“无共现”。

但用户看到的是“没有共同出现”，实际是“有，但对数低于展示门槛”。

这是一个典型的“过滤后没有报告过滤数量”的问题。

修正方式：

- 请求 `limit=200`，拿更多数据；
- 新增 `summarizePairs`，只在 `rows.length === meta.n` 时统计；
- 页面区分五种状态：
  1. 真实 0 对；
  2. 全部低于门槛；
  3. 混合（有达标、有低于）；
  4. 返回被截断；
  5. 元数据不可用。

这样用户就能看到“共 5 对，均低于 20 店门槛”，而不是空白。

### 4.13.2 R-01：未修的技术债

复核时又发现一个问题：`summarizePairs` 没有校验 `stores_both` 的有限性，也没有校验 `other_product_id` 唯一性。

如果接口缺字段，会被当成“低于门槛”；如果重复行，会重复计数。

这个问题被登记为 R-01，但当时没有修，因为冻结数据不会出现这种情况，且修复需要额外测试。

它后来被写入 BI-2-B 的 Feature Freeze 记录，作为已知技术债。

### 4.13.3 验收与冻结

BI-2-B 正式验收通过，冻结版本 `bi2b-freeze-2026-11-08`，25/25 SHA。

## 4.14 这一章改变了什么

第四章结束时，项目已经从“分析报告”变成了“可运行的产品原型”：

- P4 把分散结果整合成门店档案/诊断/联动；
- 冻结把结果变成不可变事实；
- BI-0 把数据变成只读 API；
- BI-1 把 API 变成第一批页面；
- BI-2-A/B 把商品 BI 补上。

但也留下了下一章要解决的问题：

- 页面之间还不能真正下钻；
- 返回上一页会丢筛选；
- 精确/至少组合的交互还不完整；
- `returnTo` 有安全漏洞；
- 多级返回、低 SKU 提示重复、手工 URL 冲突等细节没有处理。

这些就是 BI-2-C 的内容。
